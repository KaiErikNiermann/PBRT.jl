## Final Draft
A critical low-level consideration in the design of cross-language systems is how we deal with memory management. We can broadly divide this into two components, how long a specific variable should stay accessible, commonly known as the lifetime for a variable, and how we should deal with allocation, deallocation and access for different types across the language boundary. Naturally in the implementation of languages these concepts are strongly related as we generally want an allocation and deallocation to correspond with the expected lifetime so as not to persist unused memory. Generally speaking as a byproduct of the underlying platforms used to develop languages we usually end up with statically typed languages often relying more on manual control of memory and dynamically typed languages almost always implementing some form of runtime garbage collection mechanism. Though with time we have seen that various popular statically typed AOT compiled languages have various approaches to limit the application of low-level memory control due to its notorious risk and often problematic usage, examples include the Resource Acquisition is Initialization (RAII) paradigm most commonly associated with how C++ defined the lifetime behavior for its class implementation which is usually tied to their scope, Automatic Reference Counting which is referencing counting clang extension used in Objective-C and Swift, the Garbage Collector implementation which is bundled as the runtime for Go programs, the borrow Checker in Rust which either determines implicit lifetimes at compile time or uses explicit annotations from the programmer to determine when to deallocate an object in addition to being based strictly on destructive move semantics ensuring unique ownership of objects.

When we then look into the cross-language dynamics of different memory management systems there are a few observations to make. Despite the quite varied implementations that define memory management strategies we can create two broad categories, languages which manage memory primarily through static compile time constructs, and languages which employ runtime implementations of garbage collection. Now of note here is that while theoretically any statically typed AOT language could have a garbage collector historically there has been a preference to rely on management abstractions which more closely model the low level performant control of memory but yield enough saftey and ease of use to provide a functional trade-off. The question which we can then raise is how do we reconcile such systems. Here we can explore two key areas, firstly how can we bridge systems which employ very different strategies of memory management, and then how can we we bridge types which are implemented with specific mutation properties and levels of indirection in mind. 

An important example to look at of statically typed cross-language systems are the different attempts at bridging C++ and Rust. C++ and Rust have been mentioned a fair bit in this paper already but for good reason, a considerable amount of software has been written in C++ but as new languages emerged it became quite evident that despite the iterative improvements to the memory safety of C++ its hard match the deterministic safety of the Rust borrow checker. Yet as mentioned before, despite these languages roughly falling into the same category of languages; with both being aimed at high performance through granular control, static typing and minimal overhead inducing abstractions; they employ some considerably different memory management models. Despite these differences one thing we can observe, not just in how C++ and Rust have evolved over time but also how languages more broadly evolve is that they often either through a deliberate effort or just through natural changes implement common features. C++ adopted the aforementioned destructive move semantics, albeit implemented in a slightly different manner to Rusts. Additionally there have been various approaches, implementations and proposals to introduce Rust-style lifetime annotations into clang to get similar benefits in term of statically derivable safety guarantees about code. Where we then commonly see interoperability layers come in is in their translation and mapping of these design approaches in a manner consistent with what the programmer would expect. In the case of crubit; googles glue code generator for Rust and C++; we can see this take shape in the form of the application of clangs lifetime bounds to preform static analysis on C++ code headers to describe lifetimes in a language agnostic manner such that C++ APIs can be used on the Rust sided end with the lifetime properties of exposed methods sufficiently mapped.

Something which becomes more complex to bridge are the different implementations of move semantics, despite their abstractly similar nature the aforementioned key difference of the C++ moved-from object needing to remain in a valid state while the Rust analogue does not leads us to the fact that we need a solution in our host language (Rust) such that we do not break the expected behavior of either Rust or C++. The attempts at solutions here have primarily relied on the use of rusts pin feature, the most important property of which is that data which is pinned remains in a fixed memory location, thus ensuring that the C++ side invariant of validity till destruction is met. One other notable consideration is the notion of things being trivially movable. Something being trivially movable implies that the compiler can statically preform a move operation; meaning that it knows implicitly how to change the ownership of an object, in Rust all objects are trivially movable, in C++ this is not the case. An example of C++ objects which are not trivially movable are Polymorphic types, which is to say classes which declare virtual functions that are defined in inherited classes. As these functions rely on v-tables to work properly there is no trivial implementation which could safely define a move. The common way to deal with this discrepancy at least in the context of C++ <-> and Rust is to simply limit interoperability to types which have sufficiently close analogues in the other language such that their move semantics sufficiently overlap as to limit the complexity of interoperability layers. Now despite these differences we can still observe that due to the languages existing and evolving in a somewhat similar domain, under a well defined set of constraints we can create systems which sufficiently bridge functionality. Furthermore, despite the constraints currently placed on most interoperability systems there is research and practical work aimed at widening these constraints. A natural aspect of language evolution especially when talking about a languages type system is the goal of creating a language which allows for systems that are well defined and behave deterministically under clear constraints but also exhibit enough features to be sufficiently expressive for the domain they are usually applied in. The point of this being as languages have become and will become increasingly better at translating ideas within their domain into concrete programs so too is there a desire within the context of cross-language systems to bridge these dynamics such that we aren't as limited by the common subset when working through interoperability layers.

Languages which rely primarily on runtime GC implementations, namely JIT compiled languages exhibit certain unique distinctions in the context of cross-language systems. The nature of these distinctions stems primarily from the fact that JIT compilers commonly insert extensive metadata into types such that we have full reflection capabilities. Reflection as opposed to introspection refers to the ability to not only introspect or view the properties of type itself (as opposed to just being able to access them) but also manipulate said properties at runtime again through means aside from the direct access. Statically typed languages have adopted minimal forms of this usually as a means of expressing polymorphic types through either inserted meta-data like v-tables variations in C++ and Rust or externally passed metadata commonly known as dictionary passing used in languages like Swift and Haskell. It should be noted though that due to the profound benefits that can come from having full reflection capabilities languages like C++ and Rust have made concerted efforts to introduce such features into the language. Reflection specifically the mutation and observability of types through the provided meta-data is then naturally what is often used to implement rather expressive and performant interoperability layers. The benefit of applying reflection here comes from the fact that we in essence already have built in type wrappers, by which I mean that the metadata and exposed methods to modify types is in essence what often has to be custom built for statically typed interop. layers in the form of heading parsers and wrapper types for things we exposing as references across the language boundary. Bringing this all back to the point of memory management we can see as opposed to the need to reconcile different systems of memory management in the case of Rust and C++ in this instance we can use the metadata provided and property modifies provided by the opposing language to expose an idiomatic API front-end where the back-end then uses some common denominator bridge, such as a C-API to preform mutations without ever having to deal with the potential complexities of reconciling different GC implementations as we generally implement bridging mechanisms in a manner such that we minimize the level of copying occurring across the language boundaries, instead we work at a higher level of abstraction with cross-language calls being dedicated to describing things like mutations as opposed to copies. 

The third case we will look at is the instance where we want to bridge an AOT compiled language with a JIT compiled one. When talking about this instance in the context of memory management we see some fundamental commonalities with either of the above cases, as with communication between AOT languages and JIT'd languages we still are fundamentally reliant on some common denominator for the backend communication design, where this variant differentiates itself is in the ways we reconcile and utilize the different memory management approaches. As elaborated before we often see it that with JIT compiled languages we have metadata giving us reflective capabilities, an additional aspect of this is that especially in dynamically typed JIT compiled languages the focus on abstraction and dynamism in their design leads to the addition of having good metaprogramming tooling. Similarly to the case of two JIT compiled languages the presence of this metaprogramming tooling is then what allows us to usually have a highly generic and extensible interface for the language offering it. The same cannot be said for the AOT sided portion of this equation. The primary issue stems from the fact that if our AOT language does lack reflective capabilities to avoid copying we must fallback to the more rudimentary approach of copying over our data. While the difficulty in implementing a copy across the language boundary here is mitigated through the application of exposed metaprogramming techniques to construct the mirrored types, there are two rather painful issues we run into

1. When working with values from the JIT compiled language we often have to manually take control of the GC 
2. In the case of AOT compiled languages we often lack the reflective capabilities to bridge more complex types 

The first issue; and the one which will be focused on here; stems from the fact that to have the desired idiomatic usage of an object coming from another language we have the aforementioned two options. We either create a wrapper for a reference type or we copy over the object and map the data to the closest analogue type that exists in the other language. Now the former option is a somewhat natural choice when we can easily write idiomatic wrapper types using the abstractions provided by reflection, if we do not have these provided abstractions the resulting wrapper types can often be functional albeit limiting and therefore not very idiomatic to use. Going with the second option of copying we can can usually define a set of constrained well behaved conversion rules for generating idiomatic types coming from the JIT compiled language, though at a performance cost. Though in both approaches, reference type wrappers and copies we have the issue that data operating outside of the scope of a garbage collector is inherently not accounted for by it, thus we must manually instruct the GC to preserve any data used outside of its overview. Something to observe here is that this is somewhat akin to the issue we faced in C++ and Rust due to the nature of the disconnected ways we were bridging the data. Currently most implementations which bridge a runtime GC language with a non-GC language (i.e. one that uses reference counting, borrow checking etc.) utilize manual calls to an exposed GC API to replicate the implicit behavior it would exhibit where we operating within its domain. Though there are means of minimizing the extent to which a programmer has to manually make these calls. One example being the Jluna library for interop between C++ and Julia, its approach is to implement generic methods for boxing and unboxing (moving data between the languages) that implicitly tell the GC how to behave such that we have a constrained interface for which we can yield idiomatic C++ types without having to care about what the Julia GC does. The notable key point again here being "constrained" meaning that behaviors which go beyond the described constraints for what can be implicitly bridged given the libraries design the programmer must fall back to manual control of the GC. A potentially interesting direction to explore would be the application of implicit (through parsing and static analysis) and explicit lifetime annotations, specifically the addition of a reflective build step which can parse the annotations and either at compile time or runtime insert the necessary GC calls to preserve the liveness of a variable the GC itself cant manage.  While this is already being explored in the case of crubit through the use of an external parser over annotated C++ headers it would be interesting to see the implementation of such a mechanism compile time or runtime type reflection as a part of the language itself and not external tooling.

As a final note on memory management it would make sense to discuss some of the different ways and approaches for dealing with the low level models of types and different mutability characteristics of parameter passing strategies. Throughout this paper, the term 'idiomatically' is mentioned at various points. When we talk about using a language idiomatically, we mean using it in a way that aligns with its intended design and application, as is characteristic of the language. From the perspective of a programmer we can break this down into 3 somewhat broad categories 
1. Liveness : Any sort of memory used by the programmer should stay accessible corresponding to the defined conventions of the language we are using 
2. Utility : Features of a particular language should be usable in ways and conventions we expect them to be used in. 
3. Performance : The performance both in terms of time and memory should be a function of the particular language and the degree to which a piece of code aims to be preformant 
While these categories might not encapsulate the entire notion of idiomatic usage they do cover significant ground when we constrain ourselves to cross-language programming. Previously we talked about liveness in the context of runtime and compilation systems, which took the more top down perspective, in the following I will try to elaborate more from the other angle, namely the more concrete perspective. While there are various ways in which one could categorize the memory models of types and levels of granular detail you could go into I will use the convention adopted by Egor Zhdan [reference the talk here], this being reference types and value types. The former being types with some level of indirection and the latter being ones without. Having talked a bit about value types before I will only mention them briefly. As mentioned previously there is the quite reasonable expectation that in a cross-language context the only things treated as value types are those which are cheap to copy, which usually ends up being some overlapping set of primitives between the languages. Reference types are those which usually form the bulk of the discussion when it comes to implementation approaches. For the mutability characteristics of reference types similarly to value types we would expect similar dynamics in a cross language setting as in our host language. Thus if we do pass pointers, across the language boundary either directly or though wrappers forming another layer of indirection, in mutations in the target or guest language should be reflected in the source language if the host implements pass/call by address. The more complex case is when language which implements call by sharing for reference types calls out to a language which doesn't implement the same dynamics. Call by sharing simply put just means we create copies of references when passing them to other functions, so in terms of mutability characteristics for properties as we do with with regular call by address (passing a pointer) but with the added aspect that assignments do not mutate the original memory location. If we would want call-by-sharing to function in a cross language context with a language that does not implement these types of parameter passing dynamics it would mean more or less re-implementing these dynamics by having wrapper types in our target language which behave like the corresponding defined value references in the host language. The somewhat non-traditional nature of this convention means that it could be considered what you could call a non-goal, in that despite it contributing to the idiomatic usage of the host language its not worth the tradeoff in implementing complexity, especially as our host language evolves and specifications change. In a somewhat similar fashion closures; which are functions that capture some lexical scope of an outer function; can provide certain unique flexibilites in their application. Unfortunately just as first-class functions offer greater flexibility in design choices they similarly compound the complexity in the design of interop systems. Callbacks are usually the most basic form in which most programmers use first-class functions; if we focus on the case of a callback which does not capture scope (i.e. is not a closure); there are still a few key points to consider. Firstly we have the somewhat intuitive point that similar to normal operations across the language boundary we have to ensure that things behave idiomatically in our host language, which is to say that we must ensure that any thing returned from the callback is either wrapped correctly prior to its usage. Another point to consider is what if something goes wrong in the callback, as languages can have different (or no implicit) ways of handling exceptions this must be taken into account. I could enumerate various other considerations for the case of callbacks but ultimately alot of them reduce to a similar fact mentioned earlier that if we want safe interop there must be well defined constraints or broadly speaking systems to prevent misuse or monitor for unpredictable behavior. An interesting development by [the people who made poseidon Lua] in regards to safe memory dynamics in FFI based interop was the development by Turcotte et. al. in their application of dynamic taint analysis in their implementation of Poseidon Lua, a variant of typed Lua with an integrated C-FFI in the form of a merged type system between Lua and C and taint analysis as a means of distinguishing between memory influenced by the non-deterministic nature of C and "safe" memory from the Lua side. 

Then we have the case of closures, these as already mentioned compound the issues that we get with callbacks by the fact that they capture things within their lexical environment. The manner in which closures capture variables in a lexical scope depends on the languages implementation of binding. We can broadly classify binding into two categories, when it occurred this being compile-time or run-time binding, and how it occurs, either using value based semantics or location based semantics. There are more nuanced differences in implementations that should be considered but for the sake of context here we will limit ourselves to a more superficial overview. To elaborate on how these categories relate we can construct a table

| **Binding Type**          | **Compile-Time Binding**                       | **Runtime Binding**                         |
| ------------------------- | ---------------------------------------------- | ------------------------------------------- |
| **Binding to a Value**    | Compiler replaces the variable with the value. | Value is computed at runtime and assigned.  |
| **Binding to a Location** | Compiler assigns a **fixed memory address**.   | Memory is allocated dynamically at runtime. |
While this is somewhat of simplification it does enumerate a few of the key scenarios that have to be taken account about variables closures capture when we think about dynamics across the language boundary. More broadly speaking a lot of the dynamics come down to a point we mentioned earlier being that we must consider how the memory is being managed, in this case, within the captured scope. A mostly safe instance is the case where we have compile time value based binding, as this usually just translates into inlined values, thus is largely excluded from memory management systems as they are usually more focused on heap allocation, or more abstractly speaking bindings with some level of indirection. Which brings us to the more complex case namely languages which implement location based binding, in other words languages which bind a memory location to a variable in some lexical scope which creates a level of indirection to some underlying piece of data. In this instance we must consider the same case as we did earlier with either implement implicit control of the GC to preserve memory via the binding generator, or explicit control either via annotations such as the aforementioned lifetime annotations we have with Rust or as a feature with clang, or explicit preservation through features like memory pinning or using the GC API to override default behaviors. Again its a fair point to question in an applied context if something like this is worth implementing as opposed to adding a static or runtime constraint to prevent this all-together. While we have listed here some mostly safe case and approaches for tackling the more complex instances in practice without clear formal specifications of language dynamics there is still considerable difficulty in create safe interop for scenarios where the level of determinism is harder to accurately determine. Certain languages such as Swift especially in its generics system [reference the swift generics document] have taken great strides in creating a clear specification of behavior, but its nonetheless still difficult to create effectively safe bridges especially when we consider language features in which a semantic mismatch is considerably harder to define clear bounds of when we look at all the varied use cases of a specific feature.

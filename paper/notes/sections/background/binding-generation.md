# Binding Generation Process

## Recommendations
- Here, discuss the process and tools required to generate bindings that preserve type information across languages with different memory and type systems.
- How can binding generators handle languages with complex or polymorphic types (e.g., generics, higher-kinded types, constraints)?
- Tools and techniques used to automate the generation of these bindings.
- Common pitfalls or challenges in this process, such as managing complex data structures across languages (e.g., passing closures or lambdas).

## Draft
- **Binding Generation**
  - Once we have the type metadata, how do we generate bindings?
  - Depends on language compatibility:
    - **Similar Languages**  
      → Bindings form minimal interfaces; we might only need slight transformations to the source type to make it representable in the target language.  
      - Sometimes, no transformations are needed (though rarely).  
      - Some compilers are designed with multiple languages in mind.  
        - Example: The Cython compiler can generate C code.  

    - **Dissimilar Languages**  
      → Bindings are generally more complex. There are two common approaches:  
      - **Connected Glue Code Layers**  
        → Most implementations follow this approach. The generated bindings do not appear as idiomatic mirrored types but as wrappers exposing certain functionality that can be bridged.  
      - **Disconnected Glue Code Layers**  
        → Less common. The glue code layer is hidden, creating idiomatically mirrored types where possible.  
        - Instead of wrappers holding memory, the glue code instantiates mirrored types that can be bridged.

- **When Do We Generate Bindings?**
  - **Preprocessor Tool-Based Generation**  
    → A separate build step, usually relying on a library to perform binding generation before application execution.  
  - **Static Compiler-Based Generation**  
    → Some compilers have built-in interoperability.  
    - Example: `swiftc` (Swift compiler) has Clang embedded, allowing header parsing.  
    - This creates a disconnected glue code layer, enabling developers to use bridgeable types in an idiomatically mirrored fashion.  
  - **Runtime-Based Generation**  
    → More effective in dynamic languages.  
    - Some tools provide runtime binding generation (e.g., JavaCPP, cppyy).  
    - A key benefit: Utilizing runtime information to dynamically interact with API constructs.  
    - Useful for monomorphization and other dynamic transformations.


## Refined Draft 
- **Binding Generation**
  - Once we have the type metadata, how do we generate bindings?

Now that we have established some of the important low level considerations in the creation of binding generators, and furthermore how we manage to represent certain type properties through things like type metadata representation models we can move onto the final question of how and when to actually generate the bindings. Abstractly we can take a similar approach as we did when discussing some of the previous topics by looking firstly at the simpler case of overlap in certain design choices enabling an easier interop system and then the more complex scenario of languages which more substantial differences in design and implementation. Firstly we can asses the case of similar languages. When we use the word similar here we mean similar in their implementation of specifically the type system and the underlying associated memory models for said types. It was already noted previously that commonly for interop implementations primitives, especially those in unmanaged languages; in other words primitives which aren't boxed; can often be trivially moved across the language boundary. We can see the same notion extend to record types for languages which represent these in roughly similar fashions, an instance of this would be moving structs between rust and C++ with crubit [reference crubit] in which there is little modification applied as these types have a fundamentally similar layout given the ideological overlap in both languages being aimed at performance and hence limited runtime dynamism in tern leading to similar straightforward implementations of types. Something we can notice here when viewing things from a higher level perspective is the parallels to the case of memory management. Languages which where designed with a greater focus on compile time programming and less-so runtime features tend to have a minimal set of trivial overlap in their type design which allows often for a very constrained albeit quite functional and performant bridge to be formed. Though the constraint here being that the lack of runtime considerations lead to attempts at bridging more complex types being relegated to certain build step features, often the bidirectional header and wrapper generation process through the aforementioned parsing. When viewing this from a practical perspective it makes sense given the general application if these languages, but it unfortunately means that if we want to bridge say different implementations of generics we often cant rely on runtime flexibility or introspection as these are naturally somewhat underdeveloped features in languages which understandably aim to mitigate runtime overhead of things like detailed type metadata.

Having assessed the binding generation for the case of similar languages we can no move on to the case of dissimilar languages. Again, as we saw in the case of memory management, this leads to some interesting implementation features. To recount its a somewhat natural desire when designing glue code layers to ensure that both languages can be idiomatically used, though this desire is unfortunately somewhat antithetical in the case where languages exhibit some fundamentally different design paradigms. The result of this tends to be classifiable into two design philosophies, connected and disconnected glue code layers. Connected glue code layers tend to form the most common type of implementation, or at least they usually make up the most dominant portion of glue code system implementations. What I mean with connected layers are systems of (partially or fully) bidirectional interoperability wrappers / bindings which expose the constrained set of features which can be safely bridged, often implement implicit assurances that would be expected from the language we are getting our binding from. This is a somewhat natural implementation as it provides a very explicit and safe proxy for interacting with foreign type information, the downside naturally being that for fully idiomatic usage the programmer is left with implementing a conversion of the bridged type to an idiomatic type and ensuring the foreign language has everything safely managed. A natural question that one might have then is can we just get the full idiomatic type from the glue code? Here we have to introduce some level of nuance, in that to clarify again its commonly the case that between two languages there is a set of types we can bridge idiomatically and a set which tend to be bridged via wrappers. A particularly though understandable rare implementation is the disconnected glue code layer, which is making any aspect of interoperability when talking strictly about type usage hidden to the programmer. Which is to say, instead of types which are not easily bridged being exposed via a managed wrapper we instead use the glue code layer to implicitly generate bidirectional idiomatic types such. [show this as a graph] While in theory this sounds quite nice is comes with various downsides, a large one being that as opposed to encoding constraints on types within wrappers we have to encode the constraints within the idiomatic generation process itself, which raises two main issues 
1. To even generate an idiomatic type with constraints that we only bridge well define aspects a language needs to support such a generation process, the implementation of which can be complex
2. It naturally leads to limitations as wrapper types can expose language specific functionality that might not be shared by the common abstract idiomatic subset
A quite interesting case to make for point (2) is that if we ignore implementation complexity, one could argue that the common idiomatic subset is significantly larger when we view things from an abstract type theoretical perspective, thus the problem of bridging more complex entities in a bidirectional idiomatic fashion becomes in a sense a question of how can one encode the largest shared set of behaviors on types in the transformation layer. The main limitation of this being that often times we both cannot just ignore implementation complexity, especially if we are encoding the constraints as behaviors of the transformation process as opposed to behaviors defined for wrapper types.

  - **Runtime-Based Generation**  
    → More effective in dynamic languages.  
    - Some tools provide runtime binding generation (e.g., JavaCPP, cppyy).

    - Useful for monomorphization and other dynamic transformations.

We've now established some aspects architectural choices of the binding generation process in the case of similar and dissimilar languages we can move onto the final question of when do we actually generate the language bindings. In a sense this question somewhat mirrors the case of when to preform code generation for the concept of generics, as abstractly its a somewhat similar idea, in both cases we are in a sense generating instantiated representations of things like methods and classes based on a defined set of types, just in the case we are often generating these features as runtime wrappers, compile time cross-language headers, as opposed to instantiated generics. The 3 most relevant points at which bindings are generated are during pre-processing, compilation, or runtime. As is the case with most features discussed there aren't as clear delineations as some systems can and often do implement various of these aspects they are important to consider in their own right. The most common form we see is pre-processor based binding generation, as the name implies in this instance bindings are generated generally prior to compilation and execution of the program. Pre-processor based binding generation provides certain benefits, namely that we can preform the actual compilation with the bindings usually generated as code, not only does this mean we don't have to deal with complex runtime based implementations but as a programmer we can also get the benefit of static type auto-completion as we can directly work with the generated headers and wrapper types, as opposed to the runtime case which often inherently affords less static information. The main drawback of this is that it often comes in the form of increasing the build complexity, as we add an additional step into the process for generating the required interoperability code. Moving on we have static compiler-based generation, while less common we still see various instances of this, a common case being larger compilers which have implemented various approaches to interop in an effort to more naturally work with multi-language environments between older more legacy based languages and newer ones. One notable example being the `swiftc` compiler, which has a version of clang embedded which allows for implicit header parsing; which is to say header parsing not using a separate build tool but a feature native to the compiler itself. While it does require some minimal setup to get such a setup properly the resultant disconnected glue code layer creates an effective environment to work with Swift and C++ or Swift and its predecessor Objective-C. [reference the swiftc compiler here] The final approach for when to generate bindings is runtime-based generation. It's been mentioned a few times now that languages designed with dynamism in mind tend to be more effective at bridging certain more complex features due to their commonly reflective features; we see a similar case for the situation of when to generate bindings. Despite the fact that with runtime based binding generation we naturally do have a greater overhead, we gain the key benefit of runtime type introspection, this allows for some unique features, an important among them being that it gives us the ability to say reflect over cross language generic API methods we are calling, and then generate concrete instantiations through recompilation that can be used in a cross language environment, essentially enabling cross-language generics by simulating the dynamic type instantions which you can often lack in languages based on compile time monomorphism for generics. [maybe include a nice little diagram here] Two systems which implement such features are the JavaCPP, and cppy library which allow interop from Java to cpp and python to cpp respectively.

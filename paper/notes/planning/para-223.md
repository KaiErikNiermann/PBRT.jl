Again, as we saw in the case of memory management, this leads to some interesting implementation features. To recount its a somewhat natural desire when designing glue code layers to ensure that both languages can be idiomatically used, though this desire is unfortunately somewhat antithetical in the case where languages exhibit some fundamentally different design paradigms. The result of this tends to be classifiable into two design philosophies, connected and disconnected glue code layers. Connected glue code layers tend to form the most common type of implementation, or at least they usually make up the most dominant portion of glue code system implementations. What I mean with connected layers are systems of (partially or fully) bidirectional interoperability wrappers / bindings which expose the constrained set of features which can be safely bridged, often implement implicit assurances that would be expected from the language we are getting our binding from. This is a somewhat natural implementation as it provides a very explicit and safe proxy for interacting with foreign type information, the downside naturally being that for fully idiomatic usage the programmer is left with implementing a conversion of the bridged type to an idiomatic type and ensuring the foreign language has everything safely managed. A natural question that one might have then is can we just get the full idiomatic type from the glue code? Here we have to introduce some level of nuance, in that to clarify again its commonly the case that between two languages there is a set of types we can bridge idiomatically and a set which tend to be bridged via wrappers. A particularly though understandable rare implementation is the disconnected glue code layer, which is making any aspect of interoperability when talking strictly about type usage hidden to the programmer. Which is to say, instead of types which are not easily bridged being exposed via a managed wrapper we instead use the glue code layer to implicitly generate bidirectional idiomatic types such. While in theory this sounds quite nice is comes with various downsides, a large one being that as opposed to encoding constraints on types within wrappers we have to encode the constraints within the idiomatic generation process itself, which raises two main issues

% \subsubsection{Phase of generation}

% Now we can move onto the final question of when do we actually generate the language bindings. In a sense this question somewhat mirrors the case of when to preform code generation for the concept of generics, as abstractly its a somewhat similar idea, in both cases we are in a sense generating instantiated representations of things like methods and classes based on a defined set of types, just in the case we are often generating these features as runtime wrappers, compile time cross-language headers, as opposed to instantiated generics. The 3 most relevant points at which bindings are generated are during pre-processing, compilation, or runtime. As is the case with most features discussed there aren't as clear delineations as some systems can and often do implement various of these aspects they are important to consider in their own right.

% The most common form we see is pre-processor based binding generation, as the name implies in this instance bindings are generated generally prior to compilation and execution of the program. Pre-processor based binding generation provides certain benefits, namely that we can preform the actual compilation with the bindings usually generated as code, not only does this mean we don't have to deal with complex runtime based implementations but as a programmer we can also get the benefit of static type auto-completion as we can directly work with the generated headers and wrapper types, as opposed to the runtime case which often inherently affords less static information. The main drawback of this is that it often comes in the form of increasing the build complexity, as we add an additional step into the process for generating the required interoperability code.

% Moving on we have static compiler-based generation, while less common we still see various instances of this, a common case being larger compilers which have implemented various approaches to interop in an effort to more naturally work with multi-language environments between older more legacy based languages and newer ones. One notable example being the \texttt{swiftc} compiler, which has a version of clang embedded which allows for implicit header parsing; which is to say header parsing not using a separate build tool but a feature native to the compiler itself. While it does require some minimal setup to get such a setup properly the resultant disconnected glue code layer creates an effective environment to work with Swift and C++ or Swift and its predecessor Objective-C \cite{swift2025swiftlang}.

% The final approach for when to generate bindings is runtime-based generation. It's been mentioned a few times now that languages designed with dynamism in mind tend to be more effective at bridging certain more complex features due to their commonly reflective features; we see a similar case for the situation of when to generate bindings. Despite the fact that with runtime based binding generation we naturally do have a greater overhead, we gain the key benefit of runtime type introspection, this allows for some unique features, an important among them being that it gives us the ability to say reflect over cross language generic API methods we are calling, and then generate concrete instantiations through recompilation that can be used in a cross language environment, essentially enabling cross-language generics by simulating the dynamic type instantions which you can often lack in languages based on compile time monomorphism for generics. [maybe include a nice little diagram here] Two systems which implement such features are the JavaCPP, and cppy library which allow interop from Java to cpp and python to cpp respectively \cite{javacpp, Kundu2023Efficient}.

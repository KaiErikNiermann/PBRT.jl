Bridging an AOT-language with a JIT-compiled or interpreted one introduces some unique challenges in memory management due to asymmetries in reflection, memory management behaviors and mutability semantics. Despite the considerable improvements in performance of dynamic languges we still see AOT-languages outpreform them in various settings. The more established nature and often better performance of AOT-languages is a contributing factor to interoperability tooling aimed at bridging static-dynamic having the dynamic language positioned as the host. As we established in the two earlier sections, for static languages we typically see objects represented more directly in memory. Dynamic language design paradigms, in contrast, often represent types with more complex underlying representations. The semantic gap we have in the object representations creates a problem when wanting performant application of dynamic objects within the AOT-language. Trivially we can take the approach of just interacting with the host-language dynamic memory through guest-language thunks which interface through generated C-ABI thunks built around the host-language's API. A major issue with this wold be that the overhead introduced through the additional calls with every access could under many circumstances reasonably erase any performance benefits gained from using the AOT-language to begin with. Naturally this isn't true under all circumstances, as seen with crubit thunks can be optimized through various techniques like always inlining and ensuring no expensive memory operations are preformed across the language boundary. Nonetheless it's still not really desirable especially if we want granular control over objects within the low-level guest-language. Another approach would be to map the memory of the host-language object directly into the guest language. Constructing the host-language object within the guest-language would likely be unreasonably complex in most instances as it would require us to precisely model at least some minimum viable subset of object memory models within our guest language, akin to how crubit modelled a bidirectional representation of Rust and C++ structs. Despite this limitation we can exploit a superficial overlap in the semantics of object representations to still enable memory to be directly mapped as opposed to indirectly accessed.

  

% While the underlying memory models of object in dynamic programming languages such as Python, JavaScript, C\#, etc. can be complex due to added metadata and hidden methods to enable more dynamic behavior within the runtime, its precisely this dynamic behavior which can be leveraged. Metadata, such as how many fields a record type has, or other information about its internal layout is something which enables \textit{introspection}, i.e. the process of being able to inspect the types and properties of objects, and \textit{reflection}. Reflection is understood to build on instrospection by also allowing a program to preform self-modification, a basic example of this would be the ability to change the name of a field in a record at runtime. Many language provide API's which enable programmers to modify programs; as opposed to data; at runtime, this is commonly referred to as runtime \textit{metaprogramming}. Metaprogramming API's themselves just build on the introspection and reflection capabilities of a language.

% The first issue; and the one which will be focused on here; stems from the fact that to have the desired idiomatic usage of an object coming from another language we have the aforementioned two options. We either create a wrapper for a reference type or we copy over the object and map the data to the closest analogue type that exists in the other language. Now the former option is a somewhat natural choice when we can easily write idiomatic wrapper types using the abstractions provided by reflection, if we do not have these provided abstractions the resulting wrapper types can often be functional albeit limiting and therefore not very idiomatic to use. Going with the second option of copying we can can usually define a set of constrained well behaved conversion rules for generating idiomatic types coming from the JIT compiled language, though at a performance cost. Though in both approaches, reference type wrappers and copies we have the issue that data operating outside of the scope of a garbage collector is inherently not accounted for by it, thus we must manually instruct the GC to preserve any data used outside of its overview. Something to observe here is that this is somewhat akin to the issue we faced in C++ and Rust due to the nature of the disconnected ways we were bridging the data. Currently most implementations which bridge a runtime GC language with a non-GC language (i.e. one that uses reference counting, borrow checking etc.) utilize manual calls to an exposed GC API to replicate the implicit behavior it would exhibit where we operating within its domain. Though there are means of minimizing the extent to which a programmer has to manually make these calls. One example being the Jluna library for interop between C++ and Julia, its approach is to implement generic methods for boxing and unboxing (moving data between the languages) that implicitly tell the GC how to behave such that we have a constrained interface for which we can yield idiomatic C++ types without having to care about what the Julia GC does. The notable key point again here being "constrained" meaning that behaviors which go beyond the described constraints for what can be implicitly bridged given the libraries design the programmer must fall back to manual control of the GC. A potentially interesting direction to explore would be the application of implicit (through parsing and static analysis) and explicit lifetime annotations, specifically the addition of a reflective build step which can parse the annotations and either at compile time or runtime insert the necessary GC calls to preserve the liveness of a variable the GC itself cant manage. While this is already being explored in the case of crubit through the use of an external parser over annotated C++ headers it would be interesting to see the implementation of such a mechanism compile time or runtime type reflection as a part of the language itself and not external tooling.

Previously we talked about liveness in the context of runtime and compilation systems, which took the more top down perspective, in the following I will try to elaborate more from the other angle, namely the more concrete perspective. While there are various ways in which one could categorize the memory models of types and levels of granular detail you could go into I will use the convention adopted by Egor Zhdan \cite{zhdan2024swiftcpp}, this being reference types and value types. The former being types with some level of indirection and the latter being ones without. Having talked a bit about value types before I will only mention them briefly. As mentioned previously there is the quite reasonable expectation that in a cross-language context the only things treated as value types are those which are cheap to copy, which usually ends up being some overlapping set of primitives between the languages. Reference types are those which usually form the bulk of the discussion when it comes to implementation approaches. For the mutability characteristics of reference types similarly to value types we would expect similar dynamics in a cross language setting as in our host language. Thus if we do pass pointers, across the language boundary either directly or though wrappers forming another layer of indirection, in mutations in the guest or guest language should be reflected in the source language if the host implements pass/call by address. The more complex case is when language which implements call by sharing for reference types calls out to a language which doesn't implement the same dynamics. Call by sharing simply put just means we create copies of references when passing them to other functions, so in terms of mutability characteristics for properties as we do with with regular call by address (passing a pointer) but with the added aspect that assignments do not mutate the original memory location. If we would want call by sharing \footnote{As is often the case when it comes to naming things there is some debate in regards to the term call by sharing as its just treating a reference as a value type, but I feel this creates a unique set of properties that it warrants special consideration in the context discussed.} to function in a cross language context with a language that does not implement these types of parameter passing dynamics it would mean more or less re-implementing these dynamics by having wrapper types in our guest language which behave like the corresponding defined value references in the host language. The somewhat non-traditional nature of this convention means that it could be considered what you could call a non-goal, in that despite it contributing to the idiomatic usage of the host language its not worth the tradeoff in implementing complexity, especially as our host language evolves and specifications change.Finally two notable types to mention which is often of particular importance in an interop setting are callbacks and closures. Callbacks, when able to be passed across a language boundary, offer a beneficial feature whereby a programmer can treat a call into another language as a first-class function which provides some nice flexibility when working with foreign function calls.

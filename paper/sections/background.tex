\section{Background and Tooling}\label{s:background}

\subsection{Language Interoperability Foundations}\label{s:language_interoperability_foundations}

\subsubsection{Foreign Function Interface (FFI)}\label{s:foreign_function_interface}

Motivated by a desire to utilize some code in a \textit{guest-language}, say C, which doesnt exist in a \textit{host-language}, such as Python for example we have FFI-libraries. FFI-libraries, as the name might suggest, are typically libraries written for a host language which provide an interface, \ie some "user-friendly" abstraction, to utilize functions from a guest-language. Despite this common division of \textit{guest} and \textit{host} FFI-libraries can often have segments written in both the guest and host-language, though a commonly shared attribute and important attribute is nonetheless that these libraries, despite the bidirectional nature of how data might move, do not necessarily have bidirectional interfaces, their interfaces are often developed around the paradigm of using the guest code from the host code. Central to the development of FFI-libraries is thier reliance on a stable underlying Application Binary Interface (ABI). As the communication between languages at runtime fundamentally tied to their compilation systems; and thus the underlying ISAs we are compiling to; FFI-libraries are typically built around some common ABI. C-compilers, across platforms, have adopted a practically stable and consistent specification of how to emit code at the binary level which has led to the most common form of FFI-library being based around the C-ABI conventions. An implication of the choice to enable interoperability primarily through the stability afforded by the C-ABI and the low-level simplicity of C's semantics has led to many mainstream languages such as Julia \cite{juliaEmbedding}, Rust \cite{rustFFINomicon} or Python \cite{cffi} having basic FFI-library implementations as a part of their standard libraries or early language histories.

We can construct a minimal example of what it might look like to interact with an FFI-library as a programmer. We can write a small greet function written in C in a file called \texttt{mylib.c} which we compile to a shared object (.so) format. In Julia, Rust and Python we can then broadly describe the common steps for loading and dealing with the library \texttt{mylib.so} as follows 
\begin{enumerate}
  \item \textit{Loading} - Load the .so library into your host language code.
  \item \textit{Preperation} Prepare your host language variables for the guest-language foreign function.
  \item \textit{Usage} - Declare and/or directly access the desired foreign function through the provided FFI.
  \item \textit{Handling} - Handle the return value and possible exceptions.
\end{enumerate}

Although generally describing any piece of software which provides an abstracting for handling foreign code FFI-libraries are most commonly associated with specifically C-FFI libraries, which is to say interop tools in which C is the guest language. For the purposes of this paper we will consider FFI-libraries in the broadest possible sense so tools with arbitrary source and guest languages, albiet still generally built upon the C-ABI as the intermediary. In the examples of different languages interacting with C there are some important observations we can make, especially in regards the nature of the \textit{preperation step}. Conformance to the C-ABI means that any pieces of data which pass into this binary code compiled for said specifications must in turn also conform to this specification. Coercing data to fit the C-ABI conventions leads to a kind of linguistic bottleneck where types which have language specific usage paradigms (\ie structs with specific unique offsets or metadata) have to be deconstructed into a valid format to transfer across the language boundary and then uniquely reconstructed within our guest language if they want to mirror idiomatic usage or retain certain information. Deconstruction of types we saw with the preperation of translating language specific string formats into c-strings, reconstruction we will encounter later. 

Function signatures are another important aspect of this reliance on the C-ABI. Similarly with parameters the signatures themselves cant natively; by which I mean without an valid abstractions; exist if they don't have some low-level analogue. Generics are a prominant example of this. Due to the fact that generics tend to rely on language specific approaches for mangling overloaded function names with type specific information to create unique signatures; even if two languages have generics and maybe even similar approaches for instantiation; a limiting factor will first and foremost always be the fact that the C-ABI, by itself, does not have any specification for mangling. Hence something like we see in listing \ref{listing:extern_c_generics}, cannot exist without deviating from a pure C-ABI based FFI-library.

While then providing a stable common ground to build FFI-libraries on, the C-ABI, regardless of how much of the preperation you are able to abstract with FFI-libraries, only forms a very minimal and often limiting basis in the development of interoperability tooling. Bridging modern language features, especially ones which aid in code reuse, requires various; often language specific; strategies to evolve these libraries from their basic set of bridgable information.  

\subsubsection{Application Binary Interface (ABI)}\label{s:application_binary_interface}

An important question which arises, especially as a language grows, is how changes to its binary code generation process deviate from older ABI specifications and hence impact compatability with source code compiled with implementations based on said specifications. To mitigate communication issues between binaries compiled following different ABI conventions compilers tend to adopt specific conventions for a certain set of compiler versions, generally called \textit{partial ABI stability} as we do have a common convention for a set of compiler versions though no guarantees that this will continue indefinitely. \textit{Full ABI stability} or just \textit{ABI stability} is in contrast colloquially understood to mean that from a certain compiler version onwards all application binaries will have standardized conventions in how they interact. Swift's ABI is a recent example of reaching stability with it first introducing run-time stability in 2019 \cite{rose2019abistability}, enabling compatability between binaries at runtime as long as they guested the stable ABI (where compiled with a swiftc version >= 5.0), and compile-time stability enabling developers to use precompiled frameworks within their source code for compiler versions past >= 5.1 \cite{pestov2020library}.

Persistance of the C-ABI as the de-facto standard for implementing FFI-libraries can in large part be attributed to its stability and the legacy nature of C as a language. Despite the aforementioned limitations for more complex tasks; the C-ABI's rather constrained and minimal specification; given its existing popularity the C-ABI served as an effective basis for bridging languages who's compilers where capable of guesting its convention. Utilising often language specific features such as compile-time code generation (\ie macros in Rust, or templates in C++) like we see with CXX for Rust $\leftrightarrow$ C++ \cite{cxx} or leveraging a languages runtime models to introduce more dynamic behavior such as enabling runtime recompilation as we can the work of JavaCPP \cite{javacpp} has allowed developers to expand considerably on the more limiting core attributes of the C-ABI. Performance overhead nonetheless remains a rather fundamental aspect of working with C-ABI based FFI-libraries as most innovations still generally add more layers of indirection a variable or object must pass through. Effective memory management, specifically limiting unecessary copies and performance intensive memory manipulations, has been a crucial mitigation stategy for FFI performance overhead, often coming in the form of wrapper types such as in the case of the Julia $\leftrightarrow$ Python library JuliaCall which innovates on an older library, PyCall, by never copying mutable objects across the language boundary by default \cite{juliacall}. Integrating more complex features into C-ABI FFI-libraries to bridge two languages we can then note tends to require a clear focus on balancing the level of runtime indirection and manipulation of objects and making sure to understand how to most effectively encode and transfer objects across a primarily C-based intermediary language pipeline.   

\subsubsection{Practical Interop: C-ABI and Wasm}\label{s:practical_interop_c_abi_and_wasm}

Painting a more practical picture of what it means for an FFI-library to be C-ABI based we can introduce two languages our guest $L_g$ and our host $L_h$. Central to most FFI implemenations based around the C-ABI are usually two pieces of code, the libraries core, which generally consists of a dynamic library compiled to a platform specific C-ABI target and the guest API, which provides methods that allow accessing the dynamic library, usually built on more fundamental features provided by $L_g$'s runtime or compilation model. Conformance to the C-ABI is what tends to form the basis of how the guest API is implemented. Resulting from this choice to enable your language to be compatable with C-ABI compliant binaries, such as our dynamic library, comes with the fundamental implication that you need to coerce your types into C-compatable formats as the contractual obligation in the guest API. Coersion of types; in this instance; into a C-compatable format is what is generally known as boxing. Boxing in the more general sense can be understood as the idea of abstracting away underlying properties of types to create a generic "box" to contain them in. Programming language designers commonly use boxing in instances where the detail lost in abstraction is not necessary or wanted by the programmer in a particular instance a basic example being the \texttt{Number} class in Java. Boxing in the case of interoperability requires considerable nuance and often effort in how the Box is constructed, as the datatypes provided by C only provide the most fundamental constructs primitives, structs, etc. composing these to encode accurate sufficient information to utilize the type properly when unboxing is critical. Reconstructing the type in a way it can be effectively understood in the target language is what is generally understood by \textit{unboxing}. Unboxing has been implemented using a large variety of approaches, as its generally the goal to be able to use a type idiomatically within the context of a language most design paradigms have been centered around balancing performance with idiomatic understanding of a type.

Finding the balance between performance and idiomatic representations of types tends to come down to how effectively the low-level encoded representation of a type from the guest language can be understood and applied in the target language and vv. Naturally this leads to languages whose design philosophies are closely aligned to that of C \ie low-level performant systems based languages such as Rust, C++, Zig having a simpler path for exchanging similar types as their memory layout is similarly minimal. Conversly languages which deviate away both in execution model (JIT instead of AOT) and thus design paradigms (flexibility over performance) tend to be more complex when working with types which exhibit boxing; metadata and a more complex memory layout; within the language. Nonetheless we have seen both languages focused on dynamism exist that borrow from AOT languages such as Julia with its integration of LLVM-IR into its JIT compilation pipeline and strong tie-ins with C via its C-FFI library, and languages focused on performance such as a Rust and C++ integrate features which enable more compile-time and runtime dynamism such as Rusts macros system or C++ compile-time code generation via template meta-programming. Despite these innovations in programming languages, and the corresponding adaptations made to C-ABI based FFI-libs to bridge modern features, the increasing complexities of language semantics and execution models poses a valid question for the extent to which the C-ABI should continue to be utilizied in the development of modern interoperability tooling.   

Contrasting the C-ABIs predominantly hardware based nature a commonality we can observe with various VM-based runtime ecosystems is that as they mature, to provide the necessary extensibility to incorporate new languages, they tend to implement a platform-independent intermediate code called bytecode. Bytecode is typically executed at runtime via an interpreter as a part of a VM or compiled via an implementation of JIT compilation . Some nuance exists in the terminology as we do have some unique instances such as with Julia which, while JIT compiled, does not utilize bytecode, it instead opts for the more traditional approach of using just LLVM-IR which it compiles to native code \cite{juliaJITdocs}. Two of the most widely targeted instances of bytecode are JVM-bytecode via the GraalVM \cite{graalvmLanguagesManual} and \textit{WebAssembly} (Wasm). First announced in 2015 and having its design ratified in 2017 \cite{webassemblyFeatures}; Wasm is a byte-code format designed to be executed within web-browsers using stack-based VMs. Despite the initial runtime target of stack-based VMs; more generally the browser; nowadays there are also AOT compilers implemented to compile Wasm to native code such as WasmEdge \cite{wasmedgeAOT} or JIT compilation implementations such as GraalWasm \cite{graalvmWebAssembly}. Emscripten was an early toolchain that enabled compiling native C and C++ code to Wasm, providing a virtualized POSIX-like environment for programmers. This means that, at the API level, integrating C or C++ code with Emscripten allows native features such as file system access to use interfaces similar to those found in a standard POSIX/Linux API, requiring minimal changes to existing native code \cite{emscripten_fs_overview}. The use of a virtual POSIX-like layer is primarily motivated by the expectation that Wasm binaries will be executed within JavaScript or Wasm-supported VMs, such as browsers or Node.js. However, the close coupling between the compiled \texttt{.wasm} code, its runtime, and the ABI specification—as seen with Emscripten—can become problematic for server-side \footnote{Server-sided runtimes in this case are not to be confused with the traditional server-client model of code execution. Wasm code executing on the server-side generally just means "outside of the browser or other sandboxed runtime".} Wasm runtimes. This is because Emscripten's rapid and flexible development of POSIX emulation, while beneficial for browser compatibility, can hinder the stability and broader adoption of its binary specifications \cite{Akbary2023wasienv, akbary_wasienv_2019}. In other words, the flexibility that allows Emscripten to quickly improve POSIX emulation also makes it less suitable as a stable foundation for server-side or long-term ABI standards. 

Aiming to address the issues of ABI stability and wider adoption of Wasm into server-sided runtime models the WASI subgroup has developed and continues to work on a group of standards under the WASI name \cite{wasi_dev}. A major focus by WASI and the Bytecode Alliance in simplifying interoperability and reaching ABI stability has been the introduction of the Canonical ABI. Similarly to the C-ABI the Canonical ABI aims to standardize how data moves across language boundaries. To standardize interop with the Canonical ABI the approach taken is to use an \textit{Interface Definition Language} (IDL) called \textit{Wasm Interface Type} (WIT). WIT is used to define specifically what features a library offers, this is segmented into 3 levels of abstraction, an \textit{Interface} which represents types and functions, a \textit{World} representing a group of interfaces and a \textit{Package} representing a set of WIT files also known as \textit{Components}. Binary compatability is ensured through an interface-centric design approach. Language-specific tools generate bindings from your WIT code, creating a scaffold for your implementation. When compiled with a Canonical ABI-compliant toolchain, this ensures compatibility with any other Wasm binary compiled the same way, regardless of the source language \cite{bytecodealliance_component_model_concepts}. 

Interoperability facilitated through the Component Model and its underlying Canonical ABI has a few benefits over C-ABI based approaches. Since compatability between binaries is ensured by the nature of having an ABI compliant implementation scaffold, no boxing or unboxing between types has to occur. Canonical-ABI compliant toolchains in essence offload the necessity of boxing and unboxing as ABI compliant interface encodings are an inherent property of the generated bindings. The obvious drawback of this approach is that existing libraries which utilize language specific features not representable via WIT do require some compliant WIT-encoded representation or risk incompatibilites, though unlike the C-ABI which on the API level is based on C's type model, WIT models a much wider range of modern language features as a part of its core specification then could be trivially encoded and compiled following the C-ABIs standards. WIT is designed from the ground up as an IDL, specifically for modeling interfaces. These interfaces can then be used to generate ABI-compliant bindings. This makes WIT a strong candidate to replace C's type system as the de facto standard for interface specification in traditional FFI libraries.

\subsection{Interoperability Tool Architectures}\label{s:interoperability_tools_and_techniques}

\subsubsection{Tool Design Patterns}\label{s:tool_design_patterns}

Three important attributes shared amongst most of the popular interoperability tools, \textit{Mediation}, \textit{Validation}, and \textit{Generation}. Mediation is what tends to exist at the core of most implementations, it refers to the approach which is used to reconcile semantic differences across language boundaries. Earlier, in section \ref{s:language_interoperability_foundations}, we discussed the C-ABI as a popular choice to act as the common ground in the mediation process. A more recent alternative to ABI compatability as the common language has been API compatability. API compatability is generally more popular in managed languages, \ie JIT compiled or interpreted, which integrate APIs into their runtimes which allow extending a language with native modules that comply with the APIs high-level conventions. The primary difference between interoperability at the API and ABI level is how compatability is ensured. Compatability at the API, or source-code, level is enforced through high-level language constructs which define a contract for how to interact with some natively compiled binary. At the ABI level compatability is enforced by languages following a common platform-specific ABI specification. Though to clarify ABI and API compatability are not mutually exclusive, when an interpreted or JIT compiled language calls API compliant native code, ABI compatability must still be ensured, the idea being that if a piece of native code is compliant with a languages API, then safe, or ABI compliant, interaction should be guaranteed through the implemented higher-level constraints. 

Generation and Validation are typically the guiding factors in implementing safe API compliance. In practice what API compliance actually looks like is the bridge from the code in your guest language to idiomatic code in your host language. Code which is API compliant should typically behave according to the hosts languages semantics, which is to say in an idiomatic fashion. Bridging code occurs most often through translating guest language interfaces into ones which adopt host language semantics. The tools which interpret and generate compliant or valid interfaces, also known as bindings, to enable a safe exchange through some mediation layer, are aptly named \textit{binding generators}. Binding generators can be generally classed into two subtypes, ones aimed at creating API compliant bindings, and ones aimed at creating ABI compliant bindings. Generating API compliant bindings means the implementation tends to be focused on translating guest language interfaces into something which the host language API can interpret. On the other hand generating ABI compliant bindings revolves primarily around ensuring that the shared generated interfaces on both languages, once they are compiled, have compatability on the binary level. What differentiates ABI compliant bindings from API compliant ones is the specification of the mediation strategy they are built around. API compliant bindings use the specification of the native API from the guest language to create host language native API wrappers around guest language interfaces and data. An intermediary language is typically what forms the de-facto API specification for ABI bindings. The byproduct of relying on an intermediate language, assuming that neither the guest or the host is also the intermediary, then naturally relies on both languages needing to have compliant interfaces to allow for an exchange. In practice the difference in tooling built around API vs ABI compliant binding generation often comes down to if a language already has an API for integrating native code or not. 

Validation, which is to say actually ensuring compliance of the generated bindings can be separated intro build-time and run-time verification. At build-time verification is generally implemented through either translations or intermediate wrappers which are based on either the guest languages native API or the API of the underlying ABI we are targeting, e.g. C's interface and type semantics for the C-ABI. Build-time verification is primarily focused on establishing type-safe mediation mechanisms through conformance to the respective specifications. Run-time verification refers to approaches of validating messages across the language boundary, primarily to address language safety features (memory management, type checking, etc.) which are lost when using features from a guest language interface. To evaluate RQ (2), concerning the impacts of different language dynamics, such as a memory management approaches, on the design patterns in interoperability tooling we will take a look at both tools for languages with similar paradigms and ones aimed at more distinct domains.

Syntactically speaking, aside from very esotric or functional languages (e.g. brainfuck, Haskell), programming languages roughly follow similar patterns in their design, \ie loops, functions, data structures, variables. Semantically "similarity" is a more nuanced point to consider. We can narrow down the semantic similarity of languages if we understand it as the behaviors a language exposes to move data throughout its execution. We can break this down into languages which are focused on imperative procedures, exposing granular tools for manipulating memory, typically described as low-level or systems languages, as they commonly exists close to bare-metal machine code. Languages which are based primarily on declarative, or simply high-level constructs, which abstract common instances of imperative control flow then tend to form the other semantic group. Strictness of typing is another point which can be used to deliniate programming language semantics, but for our purposes we will use the perspective of memory management during control flow as we think it can provide some better insights in the context of evaluating RQ (2). Nowadays we do often see, especially for more mature languages, various back-end targets (JIT compilation, machine-code, etc.) which in turn leads to many languages often having features which deviate from its inital semantic focus, nonetheless the core design focus still tends to define the most common ways a language is used. 

\subsubsection{Similar languages}\label{s:similar_langs}

To evaluate tools aimed at similar languages we will use two pairs of languages, $\langle \text{C++}, \text{Rust}\rangle $ and $\langle \text{Julia}, \\ \text{Python} \rangle$. Tools which revolve around bridging Rust and C++ most commonly position C++ as the guest language with Rust being the host language. Interoperability tooling developed around languages with low-level dynamics tends to exist primarily for the purposes of reusing or rewriting libraries from an older low-level language with a newer one that has similarly good performance capabilities but innovates in areas of type and memory safety. A relevant example of this has been the different tools developed to integrate and rewrite C++ libaries within the Rust ecosystem. Driving the move towards Rust are both internal, features of the language, and related external factors, government measures \cite{ONCD2024} and industry investment \cite{RustFoundation2024}. Due to the fact that minimizing overhead is a core tenant of both Rust and C++ neither of their compilers come with built in API-compliance. Because of the established nature of legacy C codebases, what the compilers for Rust and C do have is ways to compile C-interfaces and then produce compatible binary code via the C-ABI standard. Rust-centric C++ interop tools like autocxx \cite{Taylor2025google}, cxx \cite{cxx2025} or zngur \cite{zngur2025} all fundamentally rely on Rust's and C++'s feature of declaring and compiling C compatible interfaces as the mediation strategy. The implementation for generation and validation are largely dependent on how different people answer the question of how to parse and apply header files. Bindgen \cite{rust-bindgen} uses libclang to consume C and C++ header files, which yields an Abstract Syntax Tree (AST) representation of the provided interfaces \cite{libclang}. Using the AST representation of the interface, bindgen then generates Rust source code utilizing its C-ideological. Autocxx, builds ontop of a fork of bindgen and cxx, it uses the parsed headers from bindgen to generate the custom C++-IDL used in cxx. From the generated C++-IDL it relies on cxx to generate the underling C-IDL representing the C-ABI compatable glue code. The primary benefit of integrating the generation and parsing from bindgen with the C++-IDL from cxx is that it combines automated header parsing with automated IDL generation, essentially removing all burden on the programmer to write any glue code \cite{crubit-cxx-design}. The IDL provided by cxx and its corresponding transpiling mechanism from the C++-IDL to the C-IDL also provides a more idiomatic and safe way to work with declaring and interacting with C++ interfaces in Rust then older more direct generation mechanisms \cite{chromium-rust-cpp-interop}. Zngur differntiates itself from cxx and by extension autocxx by not embedding its C++-IDL within Rust, instead choosing to have it be specified externally in a \texttt{.zng} file \cite{zngur_philosophy}. The approach Zngur takes parallels the interface driven design we discussed earlier with WIT. While most popular interop tooling is focused more prominantly on enabling cross-language dynamics through interfaces, emulating the traditional style of importing logically separated components, we do also see tooling which aims to not just have embedded cross-language IDL's but embedding foreign code itself. An instance of a language-embedding tool for Rust and C++ is the cpp crate \cite{Goffart2024mystor}. Despite still being reliant on the common C-IDL and using macro expansion to automatically generate the compliant interface definition, it takes the unique approach of allowing inline C++ code within your Rust source. At build-time the cpp crate uses macro expansion and parsing of the inline C++ code to generate a static C++ lib consisting of the inline code which it links to the final Rust binary. 

The use of compile-time code parsing and generation to implement the underlying binding generation, or even generating entire static libraries from foreign inline code, is a common pattern amongst these tools, motivated in large part by the goal of creating zero cost abstractions as both languages are generally applied in performance intensive domains. Having inline foreign source code draws some parallels to the approaches at interoperability through interpreter composition by the work of Barrett et. al. \cite{Barrett2015}, a key distinction is how the approaches optimize crossing the language boundary. Barrett employs a technique called meta-tracing; tracing by itself refers to the idea of using information at runtime to evaluate hot code, optimizing it (e.g. through specialization), and compiling it to machine code. Meta-tracing focuses on tracing the execution of an interpreter instead. A meta-tracing JIT compiler is then a JIT compiler which, as opposed to taking in the source code of a particular languages takes as an input the syntax of an interpreter, the interpreter then in turn is what executes a given source code and while doing so has its execution traced and optimized by the underling JIT compiler. A benefit of using a meta-tracing JIT compiler in this case is that, as opposed to the cpp crates language composition, we are able to use runtime information to optimimze objects crossing the language boundary. Zero cost abstractions through compile-time code generation are an effective optimization technique, but limited in their optimization capacity as long as no run-time information is used.

Tooling for Julia and Python expands considerably in a more naturalistic composition of languages. For brevity we will focus on tools in which Julia is the host language and Python is the guest language, though various design patterns are naturally mirrored. To enable interoperability both Julia and Python fundamentally rely on native language APIs. Julia, being executed by a JIT compiler written in C, naturally has a low-level C representation of objects \cite{julia_object_model}. Similarly Python; running via the CPython VM; has a C-API which allows extending the language with low-level modules conforming to its API specification. Once again we therefore see C forming the common ground here, a main difference towards $\langle \text{C++}, \text{Rust}\rangle$ tooling being the application of language specific native APIs to wrap objects, as opposed to transpiling towards the compatible intermediate C-IDL. As Python is a language built around dynamism and thus heavily managed its object representations generally have sufficient metadata for easy parsing via Julia-sided code and then wrapping the object in a mirrored interface which holds on to the underlying data, generally avoiding making any copies. Both JuliaCall \cite{juliacall} and the earlier PyCall \cite{Johnson2024JuliaPy} follow the pattern of using low-level objects parsing to create interfaces which can attach to Pythons C API object representation. To call back into Python code the JIT compiler implicitly uses Julias \texttt{ccall} mechanism which in turn interacts with Pythons C-API in essence replicating any other C-based module extension from the perspective of Pythons VM. 

\subsubsection{Dissimilar languages}\label{s:dissimilar_langs}

To assess the design patterns for tooling aimed at dissimilar languages we will look at tooling which bridges Julia and C++. As discussed in section \ref{s:similar_langs} Julia provides a C-API for low-level language extensions. Similarly for the case of bridging Python over to Julia, Julia's C-API is used as the target for wrapping code. A common inspiration we can note amongst modern tools bridging C++ to a higher level language such as Julia for the case of CxxWrap.jl \cite{libcxxwrap-julia} or Python in the case of pybind11 \cite{Jakob2024pybind} is the Boost.Python library \cite{boost_python_1_72}. The Boost C++ ecosystem are a set of libraries which are well known for their application of C++ templates and macros, in essence compile-time code generation. Boost.Python, following the Boost paradigm, uses compile-time code generation to create the compatible Python C-API shims \footnote{The most common type of shim in interoperability are thunks which adapt arguments to fit a particular calling convention and then trampoline to the actual function.}, or adapter functions, to integrate with C++ code. CxxWrap.jl follows a similar principle. On the userfacing end it provides a set of macros and functions which can be used to register C++ classes and functions. During compilation the back-end macro's then translate the interface declarations into a dynamic library which exposes the registered functionality through a combination of Julia's C-API and custom generated shims. 

Whereas CxxWrap.jl is focused on the more traditional guest-host language relationship, Cxx.jl \cite{JuliaInterop_Cxxjl} aims to achieve inline C++ code execution within Julia source code. The approach at inline foreign code execution we see in Cxx.jl differentiates itself from the cpp crate in that we don't separate out the languages at build-time and then execute them through an intermediary. Instead Cxx.jl execute the cpp code fundamentally through Julia's \texttt{llvmcall} and the application of \textit{staged functions}. Staged functions, which are declared using the \texttt{@generated} macro in Julia, are functions which implement the JIT analogue to overload resolution through compile time specialization. Julia's JIT compiler, before it generates the machine code, will first evaluate the types of the staged function's arguments, and then generate the machine code conditionally based on the types of the arguments. Cxx.jl uses staged functions to select the correct C++ function to call, in essence specializing the C++ function using Julia's JIT compiler. Once inline C++ source has associated types, Cxx.jl uses clang's frontend to generate the AST and from this emit the LLVM-IR. Using the LLVM-IR Cxx.jl then religates the actual execution of the emitted IR back to the Julia's built-in \texttt{llvmcall} mechanism. Contrasting the approach taken in Cxx.jl, we can see that it, to a degree, bypass the needed for certain optimizations either via meta-tracing or zero-cost abstractions, by simply emulating the native compilation flow of the target language \ie compile-time specialization, clang AST generated, and injected LLVM-IR execution. Cxx.jl's approach can be compared to that of the Python-C++ tool cppyy \cite{Kundu2023Efficient}. Both cppyy and Cxx.jl are able to execute inline C++ code efficiently by embedding different compilation models into the host languages runtimes. Cxx.jl implements a de-facto C++ JIT compiler by embedding parts of Clang's frontend to parse and semantically analyze C++ code, and using Julia's LLVM backend (via llvmcall) to compile and inline the resulting machine code into Julia methods. Cppyy, on the other hand, embedds the C++ interpreter cling  \cite{Vassilev2025root} to similarly execute the inline source in a way which idiomatically aligns with the underling runtime of the host language, \ie the CPython VM.

Jluna \cite{jluna}, while superficially similar to CxxWrap.jl, takes a different approach in how it works with the Julia C-API and templates to generate the necessary bindings. CxxWrap.jl, despite using macros, still relies heavily on dynamically allocated objects to generate the necessary glue code. Jluna, on the other hand, uses an almost exclusively static approach. Jluna utilizes the static information from the declared C++ classes and functions to conditionally compile or specialize meta-types which contain the necessary mechanisms and constraints to bridge themselves across the language barrier utilizing a symmetric type representation. Conceptually the idea can be understood as implementing the dynamic wrappers we see in CxxWrap.jl or similar libraries as zero-cost abstractions. A big motivation behind the design of Jluna was to provide an improved interface for Julia's C-API with the extension of enabling interoperability with C++ code. As Jluna is nonetheless still built on Julia's C-API we do still see the same limitations in performance as with other more traditional cross language tooling, \ie the overhead of boxing and unboxing in addition to a sort of cold-start problem due to the extensive application of code-generation. One way Jluna does improve upon older tooling is that through its heavy application of template metaprogramming and conditional code generation it is able to express certain cross-language dynamics in a considerably more declarative style. The declarative nature of Jluna's design stems in large part from the fact that as opposed to wrappers being designed as dynamic objects meant to contain a set of types, Jluna's meta-types are more clearly defined as self-contained static type containers acting under compile-time constraints. A major benefit of this being the additional ahead of time type saftey guarantees gained both for users when defining types and for developers when extending the library.    

\subsection{Memory Management Strategies}\label{s:memory_management}

Two important considerations come into play when discussing memory management in cross-language systems: the lifetime of a variable and how we handle allocation, deallocation, and access for different types across the language boundary. The implementation of languages often ties these concepts closely together, as we generally want allocation and deallocation to correspond with the expected lifetime of a variable to avoid persisting unused memory. Statically typed languages often rely more on manual control of memory, while dynamically typed languages typically implement some form of runtime garbage collection mechanism. Over time we have seen that various popular statically typed AOT compiled languages have developed approaches to limit the application of low-level memory control due to its notorious risks and often problematic usage. Examples include the Resource Acquisition is Initialization (RAII) paradigm in various C++ compilers like MSVC \cite{microsoft_raii}, Automatic Reference Counting (ARC) in Objective-C and Swift via the clang extension \cite{clang_arc}, the Garbage Collector in Go, and the borrow checker in Rust, which either determines implicit lifetimes at compile time or uses explicit annotations from the programmer to determine when to deallocate an object.

When examining memory management dynamics for different languages, we can observe two broad categories: languages that manage memory primarily through static compile-time constructs and languages that employ runtime implementations of heap management \ie garbage collectors. While theoretically any statically typed AOT compiled language could have a garbage collector, historically there has been a preference for management abstractions that model low-level performant control of memory while providing enough safety and ease of use. The question then becomes how to reconcile such systems, focusing on bridging systems with different memory management strategies and types with specific mutation properties and levels of indirection. To evaluate this question, we will look at memory management strategies of interoperability systems within the context of bridging AOT languages, JIT'd languages, and AOT with JIT languages. 

\subsubsection{Static strategies}\label{s:static_mem_mgmt}

Central to our analysis of interoperability in the context of AOT compiled languages will be tooling built around C++ and Rust as it provides some unique insights into abstractly similar languages but with certain considerable differance in how they handle memory management. C++ and Rust are both statically typed languages which are compiled ahead of time, they both aim to provide high performance through granular control, static typing, and minimal overhead inducing abstractions. However, they employ different memory management models. C++ has traditionally relied on memory management with RAII and reference counting, while Rust uses a borrow checker to enforce memory safety at compile time. For the sake of brevity we will constrain ourselves to talking about how specifically objects; which is to say instances of records types; are managed across the language boundary. Within C++ a record type is known as a class type which encompasses non-union and union types. The lifetime of a class-type in C++ is tied to its storage duration or temporary nature, which is determined by the context in which it is created and how its declared \ie \texttt{static}, \texttt{new} \cite{cppreference_class}. In Rust, a record type is defined as a struct, its lifetime is determined by the borrow checker. At the core of how the borrow checker works is the concept of an ownership model. Ownership is a compile-time construct in Rust that determinstically ensures that each value has a single owner, and when the owner goes out of scope, the value is automatically dropped, placing it in an invalid state. The most straightforward approach for reconciling the semantic differences in memory management between C++ and Rust is to more or less side-step the issue through the use of thunks and \textit{opaque type} pointers. 

Thunks are adapter functions \ie shims, which adapt arguments to fit a particular calling convention and then trampoline to the actual function. Tools such as cxx, autocxx, and the newer crubit \cite{crubit} in large part work by generating C-ABI compatible thunks via \texttt{extern "C"} blocks. cxx handles handles memory layouts of types primarily through opaque types, which can most simply be understood as types which persist a pointer to some memory from a guest language within a host language. Opaque types allow us to conceptually move a type around in our host language, with a core limitation that we have no actual usage of the type aside through callbacks. cxx does have a \texttt{extern "C++"} block as a part of its C++-IDL which allows the programmer to define the a Rust-sided interface implementation which internally relies on thunks. Autocxx and crubit evolve on the idea of Rust-sided wrappers by both automating their generation process. As already discussed in section \ref{s:similar_langs} autocxx uses bindgen to parse headers and then generate the C++-IDL. Crubit aims to avoid using a macro based IDL and instead directly generates the interfaces for the other language \ie Rust from C++ and C++ from Rust, and the associated thunks. 

Although cxx, autocxx and crubit generate host-language interface wrappers that internally use opaque pointers and thunks, they differ primarily in how they allocate, manage, and release the memory for the underlying guest-language objects. As these tools are primarily centered around Rust as the host-language we will focus on liveness from the perspective of Rust. An important aspect to the safe usage of objects across language boundaries is that their underlying memory stays in a valid state untill both languages no longer use the object. In theory the most trivial way to avoid premature deletion of objects is by having its ownership exclusively managed within a single language. A language taking ownership of objects it uses in a cross-language setting poses certain challenges. Native Rust objects virtually all change ownership via \textit{destructive moves}. A destructive move is one which leaves the \textit{moved-from} object in an inaccessable state. The underlying implemenation of destructive moves is more or less just a memcpy operation. While the approach of destructive moves works well in conjunction with the compile-time borrow-checker model it can't be trivially applied to Rust-sided memory which holds C++ objects. The subset of C++ types which do preseve their semantics within the context of destructive moves, \ie memcpy moves, are called \textit{trivially relocatable} (TR) types. Relocatability in essence aims to replicate Rusts destructive moves. Traditional moves in C++ via move constructors occur \textit{non-destructively}, meaning the moved-from state must have its destructor in a valid state. Trivially relocatable types are ones which are movable and provide no user-defined destructors \cite{p1144r13}. As of mid 2025 most C++ types which are TR can be identified as by either being trivial, such as scalar types, and ones which are marked with the \texttt{trivial\_abi} clang attribute \cite{clang-trivial-abi, crubit-cxx-design} \footnote{Depending on if the proposal described in P2786R11 \cite{p2786r11} is integrated into C++26 we could also see the type trait \texttt{std::is\_trivially\_relocatable} be introduced to more easily detect trivially relocatable types.}. As opposed to cxx and autocxx, crubit aims to represet the memory layout of TR C++ structs within Rust by mirroring the underlying layout \cite{crubit-struct-layout}. Mirroring the C++ layout allows crubit to construct the TR C++ objects into Rust-allocated memory. Objects which are not trivially relocatable, which is to say objects that cannot be moved with a memcpy and a destroy are a harder problem to address. Boxing via the aforementioned opaque pointers and interface wrappers avoids this issue, but comes with undesirable performance overhead. A common example brought up of non-TR objects are self-referential classes due to the fact that when being destructively relocated the internal pointers hold old memory locations; something which C++ can manage with custom move-constructors but Rust can't. Rust introduced the \texttt{Pin<T>} wrapper type to address the issue of types which are address-sensitive which need to be pinned in memory, such as self-referential types. \textit{Pinning} a location in memory provides the guarantee that the pinned value will remain located in the same place in memory from its creation till the time its dropped \cite{rust-pinning}. An early application of pinning to interoperability with C++ was with the moveit crate \cite{Young2023google} which used \texttt{Pin} to construct C++ objects into immobile Rust memory either on the stack or heap with \texttt{Pin<Box<T>>}. The same idea of using \texttt{Pin} for non-TR memory is applied in crubits design. To avoid objects having their destructors called from the C++ sided end crubit typically generates cross-language thunks as methods which pass raw pointers thus avoiding either scope based or references count based destructor calls. 

\subsubsection{Dynamic strategies}\label{s:dynamic_strategies}

What we saw in section \ref{s:similar_langs} is that for similar languages aimed at dynamism have their interoperability typically enabled through a low-level API which allows native code to communicate with higher level constructs. How objects are represented and how their lifetimes are managed once again becomes a focal point when assessing memory management. Memory management and garbage collection algorithms are typically automatic runtime processes integrated into the runtime of a particular language. JIT compiled languages such as Julia or Java, often have their memory management models defined by some allocation heuristics and collection strategies such as mark-and-sweep. The dynamics of when collection is run is also influenced importantly by memory pressure on the system and the generation classification of objects \ie how many collection phases an object has survived \cite{juliacall-gc}, \cite{digitalocean-jvm-memory-2020}. 
Because garbage collection is managed automatically and flexibly by each language's runtime, cross-language memory persistence is typically achieved by explicitly instructing the guest language's GC-via its API-to keep referenced objects alive for as long as they are needed across the language boundary. Due to the semantic gap that exists with the underlying memory layout of object models within dynamic languages its quite rare to see any attempts holding guest-language objects directly within the host-language. Wrapper types usually are host-allocated objects which hold a reference to the foreign object and interface via the languages embedding API such as the JNI for Java, Julia's C-API or Python's C-API \cite{Sengupta2023JuliaInterop}.  

\subsubsection{Hybrid strategies}\label{s:hybrid_static_dynamic}

Hybrid approaches to memory management are employed in tooling which aims to bridge languages which have fundamental gap in their memory semantics \ie managed vs unmanaged languages. It's an aim amongst most interoperability tooling to represent types idiomatically and with low-overhead. As representing objects from managed languages within unmanaged languages is considerably more non-trivial than the other way around. As such its common to see hybrid tooling taking the shape of the dynamic language handling static types. Pybind11 is a good example of the more traditional established designs. Within pybind11 the problem of object management is solved largely implicitly by interfacing with the guest language through the embedding API. Objects are typically heap allocated by default and then wrapped in a \texttt{unique\_ptr}. The C++ sided \texttt{unique\_ptr} object is then wrapped in a python-sided managed object which the GC can keep track of. Once the python-sided object is garbage collected, the default behavior is to then destroy the underlying C++ object. Embedding API's, as opposed to say regular binding generator tooling, are typically designed with the purpose of idiomatically extending dynamic languages with low-level code with a heavy focus on exposing different runtime internals. The design paradigms of embedding API's are therefore quite effective at handling the memory management of objects from guest languages, provided said guest languages can generate the necessary bindings to the embedding API.

A more recent approach mentioned when discussing tool architectures was the method of embedding the static language more directly within the dynamic runtime. A nice example of this is cppyy, which as a reminder embedds C++ within Python through the use of the cling interpreter. Abstractly speaking this isn't too dissimilar from pybind, both cppyy and pybind11 use Pythons embedding API to expose the foreign language's API. What differentiates cppyy from pybind11 is that it leverages the introspective properties of the cling interpreter to generate the necessary bindings at runtime. In a sense cppyy replaces the manual work of declaring the cpp-sided bindings with the automated introspective parsing which cling already implements. Despite the architectural differences cppyy and pybind11 ultimately end up with similar memory management properties of Python managed objects which hold references to heap allocated C++ objects. A critial takeaway from this design is that only objects which are intialized from the dynamic side, and in turn owned by the embedding API, are able to be implicitly managed. All other objects, \ie those which are not intialized from the dynamic side, have to be explicitly managed by the programmer.  

Another case to consider is how dynamic types are typically represented within static languages. One approach taken by two popular tools, namely pybind11 and Jluna, is to embedd the dynamic language's runtime within the static language. In the case of embedding the runtime within the static language both pybind11 and Jluna have implicit proxy layers that handle boxing and unboxing. We can understand these proxy layers as essentially minimal replicas of how the dynamic language runtime interacts with the embedding API. This is to say that they generally aim to roughly emulate the semantics of the dynamic language, and in kind leverage the underlying runtime \ie the embedded interpreter for memory management. Naturally the embedded interpters typically also have the ability to execute inline dynamic source code, which depending on the implementation is able to capture any scope of proxied variables as they themselves are also tied to the runtime through the embedding API. 

A final approach worth discussing is specifically the symmetric type representation of Jluna. Jluna distinguishes itself from other hybrid models by its ability to completely avoid wrappers \textit{for the programmer}. Within most interoperability tools wrappers define types which are used to represent the foreign type within the host language. Another interpretation we can have of a wrapper is that the host type which is implicitly defined by the wrappers constraints, is the actual idiomatically pure type within the host language. Wrapper constraints, broadly speaking, encapsulates a set of either static or dynamic assertions which define the semantics of how we interact with the foreign type. The most important of these constraints for record wrappers is typically the field typings, as we need the marshalling mechanisms to have a valid input type in the host which can be mapped to the target. The "front-end" representation we get from wrappers is what's then usually supposed to mirror an idiomatic type within the host language, but an important aspect is that the actual back-end semantics of the type more often then not do not conform to the host languages pure idioms. If we take for example a C++ struct from pybind11 or cppyy, on the python side we do get an object which has the same fields as the C++ struct, and even behaves for the most part like a python object, but the actual semantics of the type are driven by the host's embedding API as opposed to the actual host language runtime. When we talk about a purely idiomatic type we mean a type which is defined purely within host language semantics, \ie a regular host language type. Here we have Jluna's symmetric type representation come into play. As opposed to being used to persistently contain a foreign type, Jluna uses the notion of a wrapper as a blueprint to construct a purely idiomatic type which mirrors the foreign type. Similarly to pybind we describe a type to our interoperability layer, but instead of generating a wrapper which contains the foreign type and manages it, Jluna generates wrappers which act as specialized or type-specific translation proxies. These translation proxies are then used in conjunction with wrapper lambdas to create an invisible middle interoperability layer which yields purely idiomatic types within both the host and target language.    

\subsection{Type Interpretation Strategies}\label{s:type_interpretation}

When we talk about type interpretation strategies we are referring to how interoperability tooling is able to parse the syntax of a type and then derive a semantic understanding from which it can form some internal representation. We've touched on some of the design considerations for how we parse types when discussing design strategies in section \ref{s:tool_design_patterns}. A theme which might have already become apparent from previous mentions is that type parsing in the context of interoperability often naturally mirrors how native types are interpreted. Parallels between type parsing in interoperability tools and type interpretation in host languages offer insight into key design considerations.

Within traditional models of compilation we generally create a semantic representation of a type by first deliniating the source code into units commonly called tokens through a lexer, and then from this stream of tokens create a structural or syntactic representation of our code. A common organization of the syntactic representation is a hierarchical AST. During this \textit{front-end} analysis we typically also perform semantic analysis, one part of which is enforcing type constraints on data. Type checking in the front-end is also generally labelled as "static" type checking. In the context of interoperability tooling we are generally exclusively interested in the semantic representation of types as opposed to the entire language. Nonetheless, due to the overlapping aim of deriving a semantic-preserving manipulatable representation of a type, compiler based parsing has has considerbale influence in the design of interoperability tooling.    

One way to understand traditional compiler front-ends on a high-level is that they create a view of the source code and then generate a representation of this view which can be manpulated, such as through optimizations, in a semantic-preserving way. In the case of dynamic languages the idea of viewing code often comes in the form of runtime introspection, which was touched on briefly in section \ref{s:tool_design_patterns}. \textit{Reflection} builds on the idea of introspection by also enabling self-modification of code at runtime. An important distinction of reflection vs the transformations which occur in a compiler front-end is that reflection is not necessarily semantic-preserving across the whole program. Introspection and reflection are often significantly more variable in the schema they use to represent types but due to their increasing application and development have offered another idiom from which to derive type representations. 

\subsubsection{Static interpreting}

Two common approaches that fall into the vein of compiler, or statically-based, interpreting is either emulating compilers, \ie building a mini compiler front-end aimed at lexing and parsing specifically headers or using a compiler's AST parser and then transforming this into a domain specific representation. We can see the former approach in tools like cxx and by extension autocxx which use the syn crate \cite{dtolnay_syn} for lexing Rust tokens and then feeds this into a semi-custom parser which handles constructing an AST for the rust-sided type representation which can be used for validation and code generation. A generally harder task is transforming a full language AST into a domain specific representation. As mentioned in section \ref{s:similar_langs} the bindgen tool uses the libclang library which provides a small and stable API for some of clangs front-end internals to parse C/C++ headers. Using libclang comes with various benefits and drawbacks, a primary one described by the crubit team was that while libclang provides stability it also limits flexibility. Due to the limited flexibility provided by libclang, amongst other reasons, we have also seen instances that opted for a tighter integration with the clang front-end, such as crubit or the Swift compiler which both import features more directly from the clang front-end source code for parsing C++ headers \cite{zhdan2024swiftcpp}. Swift does also appear to use libclang in its compiler though it doesn't seem to be the primary tool for parsing C++ headers.      

\subsubsection{Dynamic interpreting}

Dynamic type interpretation is naturally most common in languages which offer the best facilities for introspection and reflection. Here we can see introspection and reflection being applied in various respects. Tools such as Jluna use the metaprogramming features provided by Jluna to implement a meta-type which represents a generic container for records, which is then used to construct the actual type representation of the mirrored foreign type with the metaprogramming tooling. We also commonly see introspection and reflection applied in interop between static and dynamic languages. Since it's common to use low-level embedding APIs to interoperate with high-level languages like Python or Julia, there's a strong incentive to exploit the linguistic overlap between these APIs and the static guest language. This enables the creation of translation mechanisms that don't depend on external tools (e.g., header parsers). As a result, developers often rely heavily on metaprogramming to manually specify types in a way that emulates dynamic introspection. These specifications are then transpiled or transformed into API-compliant code that can interface directly with the high-level language.

\section{Foundations of Language Interoperability}\label{s:background}

\subsection{FFI \& ABI Fundamentals}\label{s:language_interoperability_foundations}

\subsubsection{Foreign Function Interface (FFI)}\label{s:foreign_function_interface}

Motivated by a desire to utilize some code in a \textit{guest language}, such as C, which does not exist in a \textit{host language}, such as Python, for example, we have FFI libraries. FFI libraries, as the name might suggest, are typically libraries written for a host language that provides an interface, \ie some `user-friendly' abstraction, to utilize functions from a guest language. Despite this standard division of \textit{guest} and \textit{host}, FFI libraries can often have segments written in both the guest and host language. However, a commonly shared and important attribute is that these libraries (despite the bidirectional nature of how data might move) don't necessarily have bidirectional interfaces; their interfaces are often developed around the paradigm of using the guest code from the host code. Central to the development of FFI libraries is their reliance on a stable underlying \textit{Application Binary Interface} (ABI). As communication between languages at runtime is fundamentally tied to their compilation systems, and thus the underlying ISAs we are compiling to, FFI libraries are typically built around some standard ABI. C compilers across platforms have adopted a stable and consistent specification for emitting code at the binary level. This has resulted in the most common type of FFI library being based on C-ABI conventions. An implication of the choice to enable interoperability primarily through the stability afforded by the C-ABI and the low-level simplicity of C's semantics has led to many mainstream languages such as Julia \cite{juliaEmbedding}, Rust \cite{rustFFINomicon} or Python \cite{cffi} having basic FFI-library implementations as a part of their standard libraries or early language histories.

We can construct a minimal example of what it might look like to interact with an FFI library as a programmer. We can write a small 'greet' function in C in a file called `\texttt{mylib.c}', which we compile into a shared object (.so) format. In Julia, Rust, and Python, we can then broadly describe the common steps for loading and dealing with the library `\texttt{mylib.so}' as follows 
\begin{enumerate}
  \item \textit{Loading} - Load the .so library into your host language code.
  \item \textit{Preperation} Prepare your host language variables for the guest-language foreign function.
  \item \textit{Usage} - Declare and/or directly access the desired foreign function through the provided FFI.
  \item \textit{Handling} - Handle the return value and possible exceptions.
\end{enumerate}

Although generally describing any piece of software that provides an abstraction for handling foreign code, FFI libraries are most commonly associated with specifically C-FFI libraries, which is to say, interop tools in which C is the guest language. For this paper, we will consider FFI libraries in the broadest possible sense, so tools with arbitrary source and guest languages, albeit still generally built upon the C-ABI as the intermediary. In the examples of different languages interacting with C, there are some important observations we can make, especially regarding the nature of the \textit{preparation step}. Conformance to the C-ABI means that any pieces of data that pass into this binary code compiled for said specifications must, in turn, also conform to this specification. Coercing data to fit the C-ABI conventions leads to a kind of linguistic bottleneck where types that have language-specific usage paradigms (\ie structs with specific unique offsets or metadata) have to be deconstructed into a valid format to transfer across the language boundary and then uniquely reconstructed within our guest language if they want to mirror idiomatic usage or retain certain information. Deconstruction of types we saw during the preparation of translating language-specific string formats into C-strings and reconstruction we will encounter later. 

Function signatures are another important aspect of this reliance on the C-ABI. Similarly, with parameters, the signatures themselves cannot natively exist, by which we mean without valid abstractions if they don't have some low-level analog. Generics are a prominent example of this because generics tend to rely on language-specific approaches for mangling overloaded function names with type-specific information to create unique signatures; even if two languages have generics and maybe even similar approaches for instantiation, a limiting factor will first and foremost always be the fact that the C-ABI, by itself, does not have any specification for mangling. Hence, something as we see in listing \ref{listing:extern_c_generics} cannot exist without deviating from a pure C-ABI-based FFI-library.

While providing a stable common ground to build FFI libraries on, the C-ABI, regardless of how much of the preparation one can abstract with FFI libraries, forms a very minimal and often limited basis for the development of interoperability tooling. Marshalling modern language features, especially those that aid in code reuse, requires various, often language-specific, strategies to evolve these libraries from their basic set of bridgable information.  

\subsubsection{Application Binary Interface (ABI)}\label{s:application_binary_interface}

An important question that arises, especially as a language grows, is how changes to its binary code generation process deviate from older ABI specifications and hence impact compatibility with source code compiled with implementations based on said specifications. To mitigate communication issues between binaries compiled following different ABI conventions, compilers tend to adopt specific conventions for a particular set of compiler versions, generally called \textit{partial ABI stability} as we do have a standard convention for a set of compiler versions though no guarantees that this will continue indefinitely. \textit{Full ABI stability} or \textit{ABI stability} is, in contrast, colloquially understood to mean that from a particular compiler version onwards, all application binaries will adhere to a set of standardized conventions code generation conventions. Swift's ABI is a recent example of reaching stability with it first introducing runtime stability in 2019 \cite{rose2019abistability}, enabling compatibility between binaries at runtime as long as they guested the stable ABI (where compiled with a swiftc version >= 5.0), and compile-time stability enabling developers to use precompiled frameworks within their source code for compiler versions past >= 5.1 \cite{pestov2020library}.

The persistence of the C-ABI as the de facto standard for implementing FFI libraries can, in large part, be attributed to its stability and the legacy nature of C as a language. Despite the aforementioned limitations for more complex tasks, the C-ABI's somewhat constrained and minimal specification, given its existing popularity, served as an effective basis for bridging languages whose compilers were capable of implementing its conventions. Utilizing often language-specific features such as compile-time code generation (\ie macros in Rust, or templates in C++) as we see with CXX for Rust $\leftrightarrow$ C++ \cite{cxx} or leveraging languages runtime models to introduce more dynamic behavior such as enabling runtime recompilation as we can the work of JavaCPP \cite{javacpp} has allowed developers to expand considerably on the more limiting core attributes of the C-ABI. Performance overhead nonetheless remains a fundamental aspect of working with C-ABI-based FFI libraries, as most innovations still generally add more layers of indirection that a variable or object must pass through. Effective memory management, specifically limiting unnecessary copies and performance-intensive memory manipulations, has been a crucial mitigation strategy for FFI performance overhead, often coming in the form of wrapper types such as in the case of the Julia $\leftrightarrow$ Python library JuliaCall, which innovates on an older library, PyCall, by never copying mutable objects across the language boundary by default \cite{juliacall}. Integrating more complex features into C-ABI FFI libraries to bridge two languages tends to require a clear focus on balancing the level of runtime indirection and object manipulation, as well as understanding how to most effectively encode and transfer objects across a primarily C-based intermediary language pipeline.   

\subsection{C-ABI \& Wasm: A Comparative Lens}\label{s:practical_interop_c_abi_and_wasm}

Painting a more practical picture of what it means for an FFI library to be C-ABI based, we can introduce two languages: our guest language $L_g$ and our host language $L_h$. Central to most FFI implementations based around the C-ABI are usually two pieces of code: the library core, which generally consists of a dynamic library compiled to a platform-specific C-ABI target, and the guest API, which provides methods that allow accessing the dynamic library, usually built on more fundamental features provided by $L_g$'s runtime or compilation model. Conformance to the C-ABI is what forms the basis of how the guest API is implemented. Resulting from this choice to enable our language to be compatible with C-ABI compliant binaries, such as our dynamic library, is the fundamental implication that we need to coerce our types into C-compatible formats as a contractual obligation in the guest API. Coercion of types, in this instance, into a C-compatible format is what is generally known as boxing. Boxing, in the more general sense, can be understood as the concept of abstracting away the underlying properties of types to create a generic "box" that contains them. Programming language designers commonly use boxing in instances where the details lost in abstraction are not necessary or wanted by the programmer in a particular instance, a basic example being the \texttt{Number} class in Java. Boxing in the case of interoperability requires considerable nuance and often a considerable effort in how the Box is constructed, as the datatypes provided by C only provide the most fundamental constructs, such as primitives, structs, etc.—composing these to encode accurate and sufficient information to utilize the type properly when unboxing is critical. Reconstructing the type in a way we can effectively understand it in the target language is what is generally understood by \textit{unboxing}. Unboxing has been implemented using a large variety of approaches, as generally, the goal is to be able to use a type idiomatically within the context of a language. Most design paradigms have centered on balancing performance with an idiomatic understanding of a type.

Finding the balance between performance and idiomatic representations of types comes down to how effectively the low-level encoded representation of a type from the guest language can be understood and applied in the target language and vice versa. Naturally, this leads to languages whose design philosophies are closely aligned with that of C, \ie low-level, performant, systems-based languages such as Rust, C++, and Zig, which have a more straightforward path for exchanging similar types, as their memory layout is similarly minimal. Conversely, languages that deviate in both execution models (JIT instead of AOT) and design paradigms (flexibility over performance) tend to be more complex when working with types that exhibit boxing, require metadata, and have a more complex memory layout within the language. Nonetheless, we have seen both languages focused on dynamism exist that borrow from AOT languages such as Julia with its integration of LLVM-IR into its JIT compilation pipeline and strong tie-ins with C being both written in C and providing an extensive C-FFI library, and languages focused on performance, such as a Rust and C++ integrate features which enable more compile-time and runtime dynamism such as Rusts macros system or C++ compile-time code generation via template metaprogramming. Despite these innovations in programming languages and the corresponding adaptations made to C-ABI-based FFI libraries to bridge modern features, the increasing complexities of language semantics and execution models pose a valid question about the extent to which the C-ABI should continue to be utilized in the development of modern interoperability tooling.   

In contrast to the C-ABI's predominantly hardware-based nature, a commonality observed among various VM-based runtime ecosystems is that as they mature, they tend to implement a platform-independent intermediate code, known as bytecode, to provide the necessary extensibility for incorporating new languages. Bytecode is typically executed at runtime via an interpreter as a part of a VM or compiled via an implementation of JIT compilation. Some nuance exists in the terminology, as there are unique instances, such as with Julia, which, while JIT compiled, does not utilize bytecode; instead, it opts for the more traditional approach of using just LLVM-IR, which it compiles to native code \cite{juliaJITdocs}. Two of the most widely targeted instances of bytecode are JVM-bytecode via the GraalVM \cite{graalvmLanguagesManual} and \textit{WebAssembly} (Wasm). First announced in 2015 and having its design ratified in 2017 \cite{webassemblyFeatures}, Wasm is a bytecode format designed to be executed within web browsers using stack-based VMs. Despite the initial runtime target of stack-based VMs, there are now various runtimes, such as AOT compilers that compile Wasm to native code, like WasmEdge \cite{wasmedgeAOT}, or JIT compilation implementations like GraalWasm \cite{graalvmWebAssembly}. Emscripten was an early toolchain that enabled compiling native C and C++ code to Wasm, providing a virtualized POSIX-like environment for programmers. The provided POXIX-like environment means that, at the API level, integrating C or C++ code with Emscripten allows native features, such as file system access, to utilize interfaces similar to those found in a standard POSIX/Linux API, requiring minimal changes to existing native code \cite{emscripten_fs_overview}. The use of a virtual POSIX-like layer is primarily motivated by the expectation that Wasm binaries will be executed within JavaScript or Wasm-supported VMs, such as browsers or Node.js. However, the close coupling between the compiled \texttt{.wasm} code, its runtime, and the ABI specification—as seen with Emscripten—can become problematic for server-side \footnote{Server-sided runtimes, in this case, are not to be confused with the traditional server-client model of code execution. Wasm code executing on the server side generally means "outside of the browser or other sandboxed runtime."} Wasm runtimes. This is because Emscripten's rapid and flexible development of POSIX emulation, while beneficial for browser compatibility, can hinder the stability and broader adoption of its binary specifications \cite{Akbary2023wasienv, akbary_wasienv_2019}. In other words, the flexibility that enables Emscripten to quickly improve POSIX emulation also makes it less suitable as a stable foundation for server-side or long-term ABI standards. 

Aiming to address the issues of ABI stability and the broader adoption of Wasm into server-side runtime models, the WASI subgroup has developed and is continuing to work on a set of standards under the WASI name \cite{wasi_dev}. A significant focus by WASI and the Bytecode Alliance in simplifying interoperability and reaching ABI stability has been the introduction of the Canonical ABI. Similarly to the C-ABI, the Canonical ABI aims to standardize how data moves across language boundaries. To standardize interop with the Canonical ABI, the approach taken is to use an \textit{Interface Definition Language} (IDL) called \textit{Wasm Interface Type} (WIT). WIT is used to define specifically what features a library offers; this is segmented into three levels of abstraction: an \textit{Interface}, which represents types and functions; a \textit{World} representing a group of interfaces and a \textit{Package} representing a set of WIT files also known as \textit{Components}. Binary compatibility is ensured through an interface-centric design approach. Language-specific tools generate bindings from your WIT code, creating a scaffold for your implementation. When compiled with a Canonical ABI-compliant toolchain, this ensures compatibility with any other Wasm binary compiled the same way, regardless of the source language \cite{bytecodealliance_component_model_concepts}. 

Interoperability facilitated through the Component Model and its underlying Canonical ABI has a few benefits over C-ABI-based approaches. Since compatibility between binaries is ensured by the nature of having an ABI-compliant implementation scaffold, no boxing or unboxing between types is required. Canonical-ABI-compliant toolchains, in essence, eliminate the need for boxing and unboxing, as ABI-compliant interface encodings are an inherent property of the generated bindings. The obvious drawback of this approach is that existing libraries that utilize language-specific features not representable via WIT do require some compliant WIT-encoded representation or risk incompatibilities, though, unlike the C-ABI which on the API level is based on C's type model, WIT models a much wider range of modern language features as a part of its core specification then could be trivially encoded and compiled following the C-ABIs standards. WIT is designed from the ground up as an IDL, specifically for modeling interfaces. We can then generate ABI-compliant bindings using the modeled interfaces. This makes WIT a strong candidate to replace C's type system as the de facto standard for interface specification in traditional FFI libraries.

\subsection{Tool Architecture Patterns}\label{s:interoperability_tools_and_techniques}

There are three important attributes shared among the most popular interoperability tools: \textit{Mediation}, \textit{Validation}, and \textit{Generation}. Mediation is what tends to exist at the core of most implementations; it refers to the approach that is used to reconcile semantic differences across language boundaries. Earlier, in Section \ref{s:language_interoperability_foundations}, we discussed the C-ABI as a popular choice to serve as the common ground in the mediation process—a more recent alternative to ABI compatibility, as the common language has shifted to API compatibility. API compatibility is generally more popular in managed languages,\ie JIT compiled or interpreted, which integrate APIs into their runtimes which allow extending a language with native modules that comply with the API's high-level conventions. The primary difference between interoperability at the API and ABI levels is how compatibility is ensured. Compatibility at the API or source-code level is enforced through high-level language constructs, which define a contract for how to interact with a natively compiled binary. At the ABI level, compatibility is enforced by languages following a standard platform-specific ABI specification. Though to clarify, ABI and API compatibility are not mutually exclusive, when an interpreted or JIT-compiled language calls API-compliant native code, ABI compatibility must still be ensured, the idea being that if a piece of native code is compliant with a language API, then safe, or ABI compliant, interaction should be guaranteed through the implemented higher-level constraints. 

Generation and Validation are typically the guiding factors in implementing safe API compliance. In practice, API compliance serves as the bridge that connects code in our guest language to idiomatic code in our host language. Code that is API-compliant should typically behave according to the host's language semantics, which means it should be written in an idiomatic fashion. Marshalling code typically occurs when translating guest language interfaces into ones that adopt host language semantics. The tools that interpret and generate compliant or valid interfaces, also known as bindings, to enable a safe exchange through some mediation layer, are aptly named \textit{binding generators}. We can classify binding generators into two informal subtypes: ones aimed at creating API-compliant bindings and ones aimed at creating ABI-compliant bindings. Generating API-compliant bindings means the implementation tends to focus on translating guest language interfaces into something that the host language's API can interpret.

On the other hand, generating ABI-compliant bindings primarily revolves around ensuring that the shared generated interfaces in both languages, once compiled, have binary-level compatibility. What differentiates ABI-compliant bindings from API-compliant ones is the specification of the mediation strategy they are built around. API-compliant bindings utilize the native API specification from the guest language to create host language-native API wrappers around guest language interfaces and data. An intermediary language typically forms the de facto API specification for ABI bindings. The byproduct of relying on an intermediate language, assuming neither the guest nor the host is also the intermediary, is that both languages must have compliant interfaces to facilitate exchange. In practice, the difference in tooling built around API vs ABI-compliant binding generation often comes down to whether a language already has an API for integrating native code or not. 

Validation, ensuring compliance with the generated bindings, can be separated into build-time and run-time verification. At build time, verification is generally implemented through either translations or intermediate wrappers, which are based on either the guest language's native API or the API of the underlying ABI we are targeting, e.g., C's interface and type semantics for the C-ABI. Build-time verification is primarily focused on establishing type-safe mediation mechanisms through conformance to the respective specifications. Run-time verification refers to approaches for validating messages across language boundaries, primarily to address language safety features (such as memory management and type checking) that are lost when using features from a guest language interface. To evaluate RQ (2) concerning the impacts of different language dynamics, such as memory management approaches, on design patterns in interoperability tooling, we will examine both tools for languages with similar paradigms and those aimed at more distinct domains.

Syntactically speaking, aside from very esoteric or functional languages (e.g., brainfuck, Haskell), programming languages roughly follow similar patterns in their design, \ie loops, functions, data structures, and variables. Semantically, "similarity" is a more nuanced point to consider. We can narrow down the semantic similarity of languages if we understand it as the behaviors a language exposes to move data throughout its execution. We can break this down into languages that focus on imperative procedures, exposing granular tools for manipulating memory, typically described as low-level or system languages, as they commonly exist close to bare-metal machine code. Languages that are based primarily on declarative, or simply high-level constructs, which abstract common instances of imperative control flow, then tend to form the other semantic group. The strictness of typing is another point that can be used to delineate programming language semantics, but for our purposes, we will use the perspective of memory management during control flow as it can provide some better insights in the context of evaluating RQ (2). Nowadays, we often see, especially for more mature languages, various back-end targets (JIT compilation, machine code, etc.), which in turn lead to many languages having features that deviate from their initial semantic focus. Nonetheless, the core design focus still tends to define the most common ways a language is used. 

\subsubsection{Similar languages}\label{s:similar_langs}

To evaluate tools aimed at similar languages, we will use two pairs of languages, $\langle \text{C++}, \text{Rust}\rangle $ and $\langle \text{Julia}, \\ \text{Python} \rangle$. Tools that bridge Rust and C++ most commonly position C++ as the guest language, with Rust being the host language. Interoperability tooling developed around languages with low-level dynamics tends to exist primarily to reuse or rewrite libraries from an older low-level language with a newer one that has similarly good performance capabilities but innovates in areas such as type and memory safety. A relevant example of this is the various tools developed to integrate and rewrite C++ libraries within the Rust ecosystem. Driving the move towards Rust are both internal features of the language and related external factors, government measures \cite{ONCD2024} and industry investment \cite{RustFoundation2024}. Since minimizing overhead is a core tenant of both Rust and C++, neither of their compilers comes with built-in API compliance. Due to the established nature of legacy C codebases, compilers for Rust and C have ways to compile C interfaces and produce compatible binary code via the C ABI standard. Rust-centric C++ interop tools, such as autocxx \cite{Taylor2025google}, cxx \cite{cxx2025}, or zngur \cite{zngur2025}, all fundamentally rely on Rust's and C++'s feature of declaring and compiling C-compatible interfaces as the mediation strategy. The implementation for generation and validation is mainly dependent on how different people answer the question of how to parse and apply header files. Bindgen \cite{rust-bindgen} uses libclang to consume C and C++ header files, which yields an Abstract Syntax Tree (AST) representation of the provided interfaces \cite{libclang}. Using the AST representation of the interface, bindgen then generates Rust source code utilizing its C-ideological. Autocxx builds on top of a fork of bindgen and cxx, using the parsed headers from bindgen to generate the custom C++-IDL used in cxx. From the generated C++-IDL, it relies on cxx to generate the underlying C-IDL representing the C-ABI-compatible glue code. The primary benefit of integrating the generation and parsing from bindgen with the C++-IDL from cxx is that it combines automated header parsing with automated IDL generation, essentially removing all burden on the programmer to write any glue code \cite{crubit-cxx-design}.

The IDL provided by cxx and its corresponding transpiling mechanism from the C++-IDL to the C-IDL also provides a more idiomatic and safe way to work with declaring and interacting with C++ interfaces in Rust than older, more direct generation mechanisms \cite{chromium-rust-cpp-interop}. Zngur differentiates itself from cxx and, by extension, autocxx by not embedding its C++-IDL within Rust; instead, it chooses to have it specified externally in a \texttt{.zng} file \cite{zngur_philosophy}. The approach Zngur takes parallels the interface-driven design we discussed earlier with WIT. While most popular interop tooling focuses more prominently on enabling cross-language dynamics through interfaces, emulating the traditional style of importing logically separated components, we also see tooling that aims not just to have embedded cross-language IDLs but to embed foreign code itself. An instance of a language-embedding tool for Rust and C++ is the cpp crate \cite{Goffart2024mystor}. Despite still relying on the common C-IDL and using macro expansion to generate the compliant interface definition automatically, it takes a unique approach by allowing inline C++ code within our Rust source. At build time, the C++ crate utilizes macro expansion and parsing of the inline C++ code to generate a static C++ library comprising the inline code, which is then linked to the final Rust binary. 

The use of compile-time code parsing and generation to implement the underlying binding generation, or even generating entire static libraries from foreign inline code, is a typical pattern among these tools, motivated in large part by the goal of creating zero-cost abstractions, as both languages are generally applied in performance-intensive domains. Having inline foreign source code draws some parallels to the approaches to interoperability through interpreter composition, as seen in the work of Barrett et al. \cite{Barrett2015}. A key distinction is how these approaches optimize crossing the language boundary. Barrett employs a technique called meta-tracing; tracing, by itself, refers to the idea of using information at runtime to evaluate hot code, optimize it (e.g., through specialization), and compile it to machine code. Meta-tracing focuses on tracing the execution of an interpreter rather than the interpreter itself. A meta-tracing JIT compiler is then a JIT compiler that, unlike taking in the source code of a particular language, takes as input the syntax of an interpreter. The interpreter, in turn, executes a given source code and, while doing so, has its execution traced and optimized by the underlying JIT compiler. A benefit of using a meta-tracing JIT compiler, in this case, is that, unlike the C++ crates language composition, we are able to use runtime information to optimize objects crossing the language boundary. Zero-cost abstractions through compile-time code generation are an effective optimization technique, but their optimization capacity is limited as long as no runtime information is used.

Tooling for Julia and Python expands considerably in a more naturalistic composition of languages. For brevity, we will focus on tools where Julia is the host language and Python is the guest language, although various design patterns are naturally mirrored. To enable interoperability, both Julia and Python fundamentally rely on native language APIs. Julia, being executed by a JIT compiler written in C, naturally has a low-level C representation of objects \cite{julia_object_model}. Similarly, Python, running via the CPython VM, has a C API, which allows extending the language with low-level modules that conform to its API specification. Once again, we, therefore, see C forming the common ground here, with a primary difference between $\langle \text{C++}, \text{Rust}\rangle$ tooling being the application of language-specific native APIs to wrap objects, as opposed to transpiling towards a compatible intermediate C-IDL. As Python is a language built around dynamism, its object representations generally have sufficient metadata for easy parsing via Julia-sided code. This allows for wrapping the object in a mirrored interface that holds onto the underlying data, thereby avoiding the need for any copies. Both JuliaCall \cite{juliacall} and the earlier PyCall \cite{Johnson2024JuliaPy} follow the pattern of using low-level object parsing to create interfaces that can attach to Pythons C API object representation. To call back into Python code, the JIT compiler implicitly uses Julia's \texttt{ccall} mechanism, which in turn interacts with Python's C-API, in essence replicating any other C-based module extension from the perspective of Python's VM. 

\subsubsection{Dissimilar languages}\label{s:dissimilar_langs}

To assess the design patterns for tooling that bridges dissimilar languages, we will examine tooling that bridges Julia and C++. As discussed in Section \ref{s:similar_langs}, Julia provides a C API for low-level language extensions. Similarly, in the case of bridging Python to Julia, Julia's C API is used as the target for wrapping code. A common inspiration we can note among modern tools that bridge C++ to a higher-level language, such as Julia, is the case of CxxWrap.jl \cite{libcxxwrap-julia} or Python in the case of pybind11 \cite{Jakob2024pybind} is the Boost.Python library \cite{boost_python_1_72}. The Boost C++ ecosystem is a set of libraries well known for their application of C++ templates and macros, essentially enabling compile-time code generation. Boost. Python, following the Boost paradigm, uses compile-time code generation to create the compatible Python C-API shims \footnote{The most common type of shim in interoperability are thunks, which adapt arguments to fit a particular calling convention and then trampoline to the actual function.}, or adapter functions, to integrate with C++ code. CxxWrap.jl follows a similar principle. On the user-facing end, it provides a set of macros and functions we can use to register C++ classes and functions. During compilation, the backend macros then translate the interface declarations into a dynamic library, which exposes the registered functionality through a combination of Julia's C-API and custom-generated shims. 

Whereas CxxWrap.jl is focused on the more traditional guest-host language relationship, Cxx.jl \cite{JuliaInterop_Cxxjl} aims to achieve inline C++ code execution within Julia source code. The approach to inline foreign code execution in Cxx.jl differs from the cpp crate in that we don't separate the languages at build time and then execute them through an intermediary. Instead, Cxx.jl executes the cpp code fundamentally through Julia's \texttt{llvmcall} and the application of \textit{staged functions}. Staged functions, which are declared using the \texttt{@generated} macro in Julia, are functions that implement the JIT analog of overload resolution through compile-time specialization. Before generating machine code, Julia's JIT compiler evaluates the types of the staged function's arguments and then conditionally produces the machine code based on these types. Cxx.jl uses staged functions to select the correct C++ function to call, in essence specializing the C++ function using Julia's JIT compiler. Once the inline C++ source has associated types, Cxx.jl uses Clang's frontend to generate the AST and, from this, emit the LLVM-IR. Using the LLVM-IR Cxx.jl then relegates the actual execution of the emitted IR back to Julia's built-in \texttt{llvmcall} mechanism. Contrasting the approach taken in Cxx.jl, we can see that it, to a degree, bypasses the need for specific optimizations, either via meta-tracing or zero-cost abstractions, by simply emulating the native compilation flow of the target language, \ie compile-time specialization, a clang AST generated, and injected LLVM-IR execution. We can compare Cxx.jl's approach to that of the Python-C++ tool cppyy \cite{Kundu2023Efficient}. Both cppyy and Cxx.jl can execute inline C++ code efficiently by embedding different compilation models into the host languages runtimes. Cxx.jl implements a de facto C++ JIT compiler by embedding parts of Clang's frontend to parse and semantically analyze C++ code and using Julia's LLVM backend (via llvmcall) to compile and inline the resulting machine code into Julia methods. Cppyy, on the other hand, embeds the C++ interpreter cling  \cite{Vassilev2025root} to similarly execute the inline source in a way that idiomatically aligns with the underlying runtime of the host language, \ie the CPython VM.

Jluna \cite{jluna}, while superficially similar to CxxWrap.jl, takes a different approach in how it works with the Julia C-API and templates to generate the necessary bindings. CxxWrap.jl, despite using macros, still relies heavily on dynamically allocated objects to generate the necessary glue code. Jluna, on the other hand, uses an almost exclusively static approach. Jluna utilizes the static information from the declared C++ classes and functions to conditionally compile or specialize meta-types, which contain the necessary mechanisms and constraints to bridge themselves across the language barrier utilizing a symmetric type representation. Conceptually, we can understand the idea of implementing the dynamic wrappers we see in CxxWrap.jl or similar libraries as zero-cost abstractions. A significant motivation behind the design of Jluna was to provide an improved interface for Julia's C-API, enabling interoperability with C++ code. As Jluna is still built on Julia's C-API, we still see the same limitations in performance as with other more traditional cross-language tooling, \ie the overhead of boxing and unboxing, in addition to a sort of cold-start problem due to the extensive application of code generation. One way Jluna improves upon older tooling is through its heavy application of template metaprogramming and conditional code generation, which enables it to express specific cross-language dynamics in a considerably more declarative style. The declarative nature of Jluna's design stems in large part from the fact that, unlike wrappers being designed as dynamic objects meant to contain a set of types, Jluna's meta-types are more clearly defined as self-contained, static type containers acting under compile-time constraints. A significant benefit of this is the additional ahead-of-time type safety guarantees gained both for users when defining types and for developers when extending the library.    

\subsection{Memory Management Strategies}\label{s:memory_management}

Two important considerations come into play when discussing memory management in cross-language systems: the lifetime of a variable and how we handle allocation, deallocation, and access for different types across the language boundary. The implementation of languages often ties these concepts closely together, as we generally want allocation and deallocation to correspond with the expected lifetime of a variable to avoid persisting unused memory. Statically typed languages often rely more on manual control of memory, while dynamically typed languages typically implement some form of runtime garbage collection mechanism. Over time, we have observed that various popular statically typed AOT-compiled languages have developed approaches to limit the application of low-level memory control due to its notorious risks and often problematic usage. Examples include the Resource Acquisition is Initialization (RAII) paradigm in various C++ compilers like MSVC \cite{microsoft_raii}, Automatic Reference Counting (ARC) in Objective-C and Swift via the clang extension \cite{clang_arc}, the Garbage Collector in Go, and the borrow checker in Rust, which either determines implicit lifetimes at compile time or uses explicit annotations from the programmer to determine when to deallocate an object.

When examining memory management dynamics for different languages, we can observe two broad categories: languages that manage memory primarily through static compile-time constructs and languages that employ runtime implementations of heap management,  \ie garbage collectors. While theoretically, any statically typed AOT-compiled language could have a garbage collector, historically, there has been a preference for management abstractions that model low-level, performant control of memory while providing sufficient safety and ease of use. The question then becomes how to reconcile such systems, focusing on bridging systems with different memory management strategies and types with specific mutation properties and levels of indirection. To evaluate this question, we will examine the memory management strategies of interoperability systems within the context of bridging AOT languages, JIT languages, and AOT with JIT languages. 

\subsubsection{Static strategies}\label{s:static_mem_mgmt}

Central to our analysis of interoperability in the context of AOT-compiled languages will be tooling built around C++ and Rust, as it provides some unique insights into abstractly similar languages but with specific, considerable differences in how they handle memory management. C++ and Rust are both statically typed languages that are compiled ahead of time; they both aim to provide high performance through granular control, static typing, and minimal overhead-inducing abstractions. However, they employ different memory management models. C++ has traditionally relied on memory management techniques such as RAII and reference counting, whereas Rust utilizes a borrow checker to enforce memory safety at compile time. For the sake of brevity, we will limit our discussion to how objects, which are instances of record types, are managed across the language boundary. Within C++, a record type is referred to as a class type, which encompasses both non-union and union types. The lifetime of a class type in C++ is tied to its storage duration or temporary nature, which is determined by the context in which it's created and how it's declared, \ie \texttt{static}, \texttt{new} \cite{cppreference_class}. In Rust, a record type is defined as a struct, and the borrow checker determines its lifetime. At the core of how the borrow checker works is the concept of an ownership model. Ownership is a compile-time construct in Rust that deterministically ensures each value has a single owner. When the owner goes out of scope, the value is automatically dropped, placing it in an invalid state. The most straightforward approach for reconciling the semantic differences in memory management between C++ and Rust is to more or less side-step the issue through the use of thunks and \textit{opaque type} pointers. 

Thunks are adapter functions, \ie shims, which adapt arguments to fit a particular calling convention and then trampoline to the actual function. Tools such as cxx, autocxx, and the newer Crubit \cite{crubit} work extensively by generating C-ABI compatible thunks via \texttt{extern "C"} blocks. Cxx handles memory layouts of types primarily through opaque types, which we can understand as types that persist as a pointer to some memory from a guest language within a host language. Opaque types enable us to conceptually move a type around in our host language, with a core limitation that we have no actual usage of the type beyond callbacks. Cxx does have a \texttt{extern "C++"} block as a part of its C++-IDL, which allows the programmer to define the Rust-sided interface implementation that internally relies on thunks. Autocxx and Crubit evolved the idea of Rust-sided wrappers by automating their generation process. As already discussed in section \ref{s:similar_langs}, autocxx uses bindgen to parse headers and then generate the C++-IDL. Crubit aims to avoid using a macro-based IDL and instead directly generates the interfaces for the other language, \ie Rust from C++ and C++ from Rust, and the associated thunks. 

Although cxx, autocxx, and Crubit generate host-language interface wrappers that internally use opaque pointers and thunks, they differ primarily in how they allocate, manage, and release the memory for the underlying guest-language objects. As these tools are primarily centered on Rust as the host language, we will focus on liveness from the Rust perspective. An important aspect of the safe usage of objects across language boundaries is that their underlying memory remains in a valid state until both languages no longer use the object. In theory, the most trivial way to avoid premature deletion of objects is by having their ownership exclusively managed within a single language. A language taking ownership of objects it uses in a cross-language setting poses specific challenges. Native Rust objects virtually all change ownership via \textit{destructive moves}. A destructive move leaves the \textit{moved-from} object in an inaccessible state. The underlying implementation of destructive moves is essentially a memcpy operation. While the approach of destructive moves works well in conjunction with the compile-time borrow-checker model, we cannot trivially apply it to Rust-sided memory, which holds C++ objects. The subset of C++ types that do preserve their semantics within the context of destructive moves, \ie memcpy moves, are called \textit{trivially relocatable} (TR) types. Relocatability, in essence, aims to replicate Rust's destructive moves. Traditional moves in C++ via move constructors occur \textit{non-destructively}, meaning the moved-from state must have its destructor in a valid state \cite{hartzell2021cppmove}. Trivially relocatable types are movable and provide no user-defined destructors \cite{p1144r13}. As of mid-2025, most C++ types which are TR can be identified by either being trivial, such as scalar types, and ones that are marked with the \texttt{trivial\_abi} clang attribute \cite{clang-trivial-abi, crubit-cxx-design} \footnote{Depending on if the proposal described in P2786R11 \cite{p2786r11} is integrated into C++26 we could also see the type trait \texttt{std::is\_trivially\_relocatable} be introduced to more easily detect trivially relocatable types.}. Unlike cxx and autocxx, Crubit aims to represent the memory layout of TR C++ structs within Rust by mirroring the underlying layout \cite{crubit-struct-layout}. Mirroring the C++ layout enables Crubit to construct TR C++ objects in Rust-allocated memory. Objects that are not trivially relocatable, which is to say objects that we are unable to move with a memcpy and a destroy, are a more complicated problem to address. Boxing via the aforementioned opaque pointers and interface wrappers avoids this issue but comes with undesirable performance overhead. A typical example of non-TR objects is self-referential classes, as they retain internal pointers to old memory locations when destructively relocated. Self-referential classes are something that C++ can manage with custom move-constructors, but Rust cannot. Rust introduced the \texttt{Pin<T>} wrapper type to address the issue of types that are address-sensitive and require pinning in memory, such as self-referential types. \textit{Pinning} a location in memory provides the guarantee that the pinned value will remain located in the same place in memory from its creation till the time it's dropped \cite{rust-pinning}. An early application of pinning to interoperability with C++ was with the MoveIt crate \cite{Young2023google}, which used \texttt{Pin} to construct C++ objects into immobile Rust memory, either on the stack or heap, with \texttt{Pin<Box<T>>}. The same idea of using \texttt{Pin} for non-TR memory is applied in Crubit's design. To avoid objects having their destructors called from the C++-sided end, Crubit typically generates cross-language thunks as methods that pass raw pointers, thus avoiding either scope-based or reference count-based destructor calls. 

\subsubsection{Dynamic strategies}\label{s:dynamic_strategies}

What we saw in Section \ref{s:similar_langs} is that for similar languages aimed at dynamism, their interoperability is typically enabled through a low-level API, which allows native code to communicate with higher-level constructs. How we represent objects and manage their lifetimes once again becomes a focal point when assessing memory management. Memory management and garbage collection algorithms are typically automatic runtime processes integrated into the runtime of a particular language. JIT-compiled languages, such as Julia or Java, often have their memory management models defined by allocation heuristics and collection strategies, including mark-and-sweep. The dynamics of when we run gc-collection is also influenced significantly by memory pressure on the system and the generation classification of objects,  \ie how many collection phases an object has survived \cite{juliacall-gc}, \cite{digitalocean-jvm-memory-2020}. 

Because garbage collection is managed automatically and flexibly by each language's runtime, cross-language memory persistence is typically achieved by explicitly instructing the guest language's garbage collector (GC) via its API to keep referenced objects alive for as long as they are needed across the language boundary. Due to the semantic gap that exists between the underlying memory layout of object models within dynamic languages, it's rare to see attempts to hold guest-language objects directly within the host language. Wrapper types are usually host-allocated objects that hold a reference to the foreign object and interface via the language's embedding API, such as the JNI for Java, Julia's C-API, or Python's C-API \cite{Sengupta2023JuliaInterop}.  

\subsubsection{Hybrid strategies}\label{s:hybrid_static_dynamic}

Hybrid approaches to memory management are employed in tooling, which aims to bridge languages that have fundamental gaps in their memory semantics, \ie managed vs. unmanaged languages. it's an aim among most interoperability tooling to represent types idiomatically and with low overhead. Representing objects from managed languages within unmanaged languages is considerably more non-trivial than the other way around. As such, it's common to see hybrid tooling taking the shape of the dynamic language handling static types. Pybind11 is a good example of the more traditional established designs. Within pybind11, the problem of object management is solved largely implicitly by interfacing with the guest language through the embedding API. Objects are typically heap allocated by default and then wrapped in a \texttt{unique\_ptr}. The C++-sided \texttt{unique\_ptr} object is then wrapped in a python-sided managed object, which the GC can keep track of. Once the Python-side object is garbage collected, the default behavior is to destroy the underlying C++ object as well. Embedding APIs, as opposed to, say, regular binding generator tooling, are typically designed to idiomatically extend dynamic languages with low-level code with a heavy focus on exposing different runtime internals. The design paradigms of embedding APIs are, therefore, quite effective at handling the memory management of objects from guest languages, provided said guest languages can generate the necessary bindings to the embedding API.

A more recent approach mentioned when discussing tool architectures was the method of embedding the static language more directly within the dynamic runtime. A nice example of this is cppyy, which, as a reminder, embeds C++ within Python through the use of the cling interpreter. Abstractly speaking, this is not too dissimilar from pybind11; both cppyy and pybind11 use Python's embedding API to expose the foreign language's API. What differentiates cppyy from pybind11 is that it leverages the introspective properties of the cling interpreter to generate the necessary bindings at runtime. In a sense, cppyy replaces the manual work of declaring the C++-sided bindings with the automated introspective parsing that Cling already implements. Despite the architectural differences, cppyy and pybind11 ultimately result in similar memory management properties for Python-managed objects that hold references to heap-allocated C++ objects. A critical takeaway from this design is that only objects initiated from the dynamic side and, in turn, owned by the embedding API can be implicitly managed. All other objects, \ie those which are not initialized from the dynamic side, have to be explicitly managed by the programmer.  

Another case to consider is how dynamic types are typically represented within static languages. One approach taken by two popular tools, namely pybind11, and Jluna, is to embed the dynamic language's runtime within the static language. In the case of embedding the runtime within the static language, both pybind11 and Jluna have implicit proxy layers that handle boxing and unboxing. These proxy layers are essentially minimal replicas of how the dynamic language runtime interacts with the embedding API. They generally aim to roughly emulate the semantics of the dynamic language and, in kind, leverage the underlying runtime,  \ie the embedded interpreter for memory management. Naturally, the embedded interpreters typically also execute inline dynamic source code, which, depending on the implementation, can capture any scope of proxied variables as they are tied to the runtime through the embedding API. 

A final approach worth discussing is specifically the symmetric type representation of Jluna. Jluna distinguishes itself from other hybrid models by its ability to altogether avoid wrappers \textit{for the programmer}. Within most interoperability tools, wrappers define types that represent the foreign type within the host language. Another interpretation we can have of a wrapper is that the host type, which is implicitly defined by the wrapper's constraints, is the actual idiomatically pure type within the host language. Wrapper constraints encapsulate a set of either static or dynamic assertions that define the semantics of how we interact with the foreign type. The most important of these constraints for record wrappers is typically the field typings, as we need the marshaling mechanisms to have a valid input type in the host that can be mapped to the target. The "front-end" representation we get from wrappers is what is then usually intended to mirror an idiomatic type within the host language; however, an important aspect is that the actual back-end semantics of the type, more often than not, don't conform to the host language's pure idioms. Let's take, for example, a C++ struct from pybind11 or cppyy on the Python side. We obtain an object that has the same fields as the C++ struct and behaves, for the most part, like a Python object; however, the actual semantics of the type are driven by the host's embedding API rather than the host language runtime itself. When we talk about a purely idiomatic type, we mean a type that is defined purely within host language semantics,  \ie a regular host language type. Here, we have Jluna's symmetric type representation come into play. Unlike being used to contain a foreign type persistently, Jluna utilizes the notion of a wrapper as a blueprint to construct a purely idiomatic type that mirrors the foreign type. Similarly to pybind11, we describe a type of our interoperability layer. However, instead of generating a wrapper that contains the foreign type and manages it, Jluna generates wrappers that act as specialized or type-specific translation proxies. These translation proxies are then used in conjunction with wrapper lambdas to create an invisible middle layer of interoperability that yields purely idiomatic types within both the host and target languages.    

\subsection{Type-Representation Strategies}\label{s:type_interpretation}

When we discuss type representation strategies, we refer to how interoperability tooling parses the syntax of a type and derives a semantic understanding from it, allowing it to form an internal representation. We have touched on some of the design considerations for how we parse types when discussing design strategies in section \ref{s:interoperability_tools}. A theme that might have already become apparent from previous mentions is that type parsing in the context of interoperability often naturally mirrors how native types are interpreted. Parallels between type parsing in interoperability tools and type interpretation in host languages offer insight into key design considerations.

Within traditional models of compilation, we generally create a semantic representation of a type by first delineating the source code into units commonly called tokens through a lexer and then, from this stream of tokens, create a structural or syntactic representation of our code. A common organization of the syntactic representation is a hierarchical AST. During this \textit{front-end} analysis, we typically also perform semantic analysis, which includes enforcing type constraints on data. Type checking in the front end is also commonly referred to as "static" type checking. In the context of interoperability tooling, we are generally exclusively interested in the semantic representation of types as opposed to the entire language. Nonetheless, due to the overlapping aim of deriving a semantic-preserving manipulatable representation of a type, compiler-based parsing has considerable influence on the design of interoperability tooling.    

One way to understand traditional compiler front-ends at a high level is that they create a view of the source code and then generate a representation of this view, which can be manipulated, such as through optimizations, in a semantically preserving way. In the case of dynamic languages, the idea of viewing code often comes in the form of runtime introspection, which was touched on briefly in section \ref{s:interoperability_tools}. \textit{Reflection} builds on the idea of introspection by also enabling self-modification of code at runtime. A key distinction between Reflection and the transformations that occur in a compiler front-end is that Reflection is not necessarily semantic-preserving across the entire program. Introspection and Reflection are often significantly more variable in the schema they use to represent types. However, due to their increasing application and development, they have offered another idiom from which to derive type representations. 

\subsubsection{Static interpreting}

Two common approaches that fall into the vein of the compiler, or statically-based, interpreting are either emulating compilers, \ie building a mini compiler front-end aimed at lexing and parsing specifically headers, or using a compiler's AST parser and then transforming this into a domain-specific representation. We can see the former approach in tools like cxx and, by extension, autocxx, which use the syn crate \cite{dtolnay_syn} for lexing Rust tokens and then feeds this into a semi-custom parser that handles constructing an AST for the rust-sided type representation, which can be used for validation and code generation. A generally more challenging task is transforming a whole language AST into a domain-specific representation. As mentioned in Section \ref{s:similar_langs}, the bindgen tool uses the libclang library, which provides a small and stable API for some of Clang's front-end internals to parse C/C++ headers. Using libclang comes with various benefits and drawbacks; a primary one, as described by the Crubit team, is that while libclang provides stability, it also limits flexibility. Due to the limited flexibility provided by libclang, amongst other reasons, we have also seen instances that opted for a tighter integration with the clang front-end, such as Crubit or the Swift compiler, which both import features more directly from the clang front-end source code for parsing C++ headers \cite{zhdan2024swiftcpp}. Swift also appears to use libclang in its compiler, although it does not seem to be the primary tool for parsing C++ headers.      

\subsubsection{Dynamic interpreting}

Dynamic type interpretation is most commonly found in languages that offer the best facilities for introspection and reflection. Here, we can see introspection and reflection being applied in various respects. Tools such as Jluna use the metaprogramming features provided by Jluna to implement a meta-type that represents a generic container for records, which is then used to construct the actual type representation of the mirrored foreign type with the metaprogramming tooling. We also commonly see introspection and reflection applied in interop between static and dynamic languages. Since it's common to use low-level embedding APIs to interoperate with high-level languages like Python or Julia, there is a strong incentive to exploit the linguistic overlap between these APIs and the static guest language. This enables the creation of translation mechanisms that don't depend on external tools (e.g., header parsers). As a result, developers often rely heavily on metaprogramming to manually specify types in a way that emulates dynamic introspection. These specifications are then transpiled or transformed into API-compliant code that can interface directly with the high-level language.

\section{Formalising Interoperability}\label{s:record_type}

Specific shared patterns emerge when we discuss the design of various interoperability tools. The source of these shared patterns, in large part, stems from specific attributes of the problem they aim to address. One of these attributes is that, similarly to compilers, interoperability tools typically take as an input some static source and then, once compiled, yield a program that enables dynamic behaviors constrained by the semantics of the input source. We can understand this as a form of partial computation, which provides a potential lens through which we can discuss interoperability tooling within the context of the existing, well-established framework of partial computation.

How types are represented within interoperability tooling becomes another important cornerstone of their design. Type representations, \ie their models, such as how generic wrappers are defined, generally define the constraints on how we bridge and interact with types across the language boundary. The constraints of type representations often become more prevalent as language-specific models have less and less overlap, which can be leveraged to define common ground. As such, there is value in not just understanding the type models of individual languages but also their relations within a shared theoretical framework. In the latter half of this section, we will discuss specifically how dependent type theory can provide a clear picture in motivating confident, practical design choices for the joint interoperability tool.   

\subsection{Interop Tools as Partial Evaluators}\label{s:interoperability_tools}

\subsubsection{Metaprogramming}

As the practical anchor for our discussion of partial evaluation we will use the concept of metaprogramming, specficially within C++. We've mentioned previously that metaprogramming is used in various interoperability tools such as Jluna and Pybind11 to generate the necessary bindings. When viewed from the abstract perspective whats happening in tools that employ metaprogramming is that the interfaces which specify the types generally don't manipulate data in any sense, but rather they manipulates code,  \ie generate instantiated bindings. Manipulating code is a key aspect of metaprogramming, which is generally defined as the ability to write programs that can manipulate other programs. An interesting perspective and previously explored perspective on metaprogramming is that its instantiation or specialization process is a form of partial evaluation \cite{Veldhuizen1998}.

In practice, implementing $G^2$ requires us to work at a higher level of abstraction. Instead of writing generic logic meant to apply to the set of types we wish to bridge, we would define the abstract attributes of a binding generator itself. This means that boxing and unboxing logic would be defined in a way that is independent of the specific types being bridged. Stated differently, instead of writing bridging functions for a set of types, we would use them for kinds or families of types. A basic example of this would be that instead of defining unboxing functions for, say, integers, booleans, floats, etc., we would define a generic unboxing function for the \textit{primitive} type family, which would be specialized for each primitive type. One instance that comes close is the Simplified Wrapper and Interface Generator (SWIG) framework \cite{Fulton2025swig}. While this tool technically accepts arbitrary target language specifications, its host languages are limited to C and C++. Furthermore, the tool does not specialize in a binding generator for the languages; instead, it directly generates the bindings based on the parsed C/C++ headers. Nonetheless, it does present an interesting case of a binding generator tool that leverages higher abstractions to define a more generic binding generator.   

The complexity of implementing an accurate second Futurama projection is, in large part, a function of how we approach making the actual binding generator logic generic. Generating the correct methods for boxing and unboxing is relatively straightforward in theory, as it's more or less analogous to just specializing some generic code over a set of input types. The more complex part is how we can effectively generalize the logic of actually generating the value-level type conversions. One of the reasons why SWIG is specifically able to get at least part of the way there is that it leverages the fact that many languages can create binding generators that have similar embedding APIs, specifically for C. However, this only works because the interoperability context is narrowly scoped. For a more principled and fully general second Futamura projection, the generator logic would need to abstract not just over surface syntax or API calls but over deeper interoperability semantics — including memory ownership, mutability, and type representation — across a much more diverse set of host and target languages. This significantly increases the design complexity and is part of why such systems remain largely theoretical.

An important thing to take away from the idea of thinking about binding generators as partial evaluators is that we end up with a more well-defined separation of concerns between different steps of the binding generation process, which can offer up a more effective foundation for implementing future generators in a more uniform and preformant manner by isolating the statically known specifications from the actual implementation logic and viewing the implementation itself as a specializer over the specification as opposed to being a direct implementation of interop logic. The relevance here is that it supports the fact that any extensions made to the type specification should be done in a way that does not compromise the existing logic of the binding generator, ensuring we maintain this quality of separation of concerns.

\subsection{Records as Dependent Product Types}\label{s:record_type_model}

Records, in the most straightforward sense, are a collection of fields indexed by a set of labels corresponding to some value. The most basic form of indexing is typically implemented as an offset-based access to a contiguous block of memory. When discussing records within a formal framework, there are three prominent paths we can take. The first approach would be to view records through the object calculus ($\zeta$-calculus) framework from Abadi et al. \cite{Abadi1996Theory}, which was motivated by a desire to formalize the semantics of object-oriented languages in the same way different $\lambda$-calculi act as the foundation for more procedural languages. 

\subsubsection{Different Models of Records}

\begin{definition}[Records in the $\zeta$-calculus]
Within the $\zeta$-calculus, records, or more broadly objects, are defined as a collection $i\in[1, n]$ of labels $l_i$ and their corresponding values consisting of methods $\zeta(x_i)b_i$. In full, the notation is 

\begin{equation}
  o = [l_i \mapsto \zeta(x_i)b_i]_{i=1}^n
\end{equation}

The method $\zeta(x_i)b_i$ is intended to represent the concept of a `\texttt{self}' parameter, which each value of a record can access. Hence, a field access $o.l_i$ would be defined by the reduction. 

\begin{equation}
  o.l_i \rightarrow \zeta(x_i)b_i[o/x_i]
\end{equation}

This is functionally no different from how most object-oriented languages with the concepts of a `\texttt{self}' or `\texttt{this}' parameter work. 

\end{definition}

The second way records are commonly modeled in an intuitive sense is through a structured ontological perspective. To illustrate this, let's consider the following sentence and work our way through it. 

\begin{center}
  \begin{quote}
    \textit{a student writes a thesis.}
  \end{quote}
\end{center}

We can create a structured ontology of this using the grammar defined by Montague \cite{montague1970english}, which would look like the following. 

\[
  \begin{aligned}
    \text{`a'} & : \text{Determiner}  & = &\  \lambda Q.\ \exists (P(x) \land Q(x)) \\
    \text{`(a) student'} & : \text{Noun}  & = &\  \lambda x.\ \text{STUDENT}(x) \\
    \text{`writes'} & : \text{Transverb}  & = &\  \lambda x.\ \exists y. \text{WRITES}(x, y) \\
    \text{`(a) thesis'} & : \text{Noun}  & = &\  \lambda y.\ \text{THESIS}(y) 
  \end{aligned}
\]\footnote{A determiner is a word or affix that introduces a noun and expresses its reference in the context, such as "a," "the," "some," or "every."}

By combining these, we can express the sentence as follows. 

\begin{equation}\label{eq:student_thesis}
  \exists x (\text{STUDENT}(x) \land \exists y (\text{THESIS}(y) \land \text{WRITES}(x, y)))
\end{equation}

The resulting proposition we get in \ref{eq:student_thesis} allows us to express the idea that there exists a student $x$ who writes a thesis $y$. However, as a proposition, it's limited to only expressing a predicate; from the proposition alone, we cannot derive any information about who the student is or what the thesis is. Nonetheless, this grammar conceptually captures the early idea of what constitutes a valid record initialization. In our example, the values of the record are the variables $x$ and $y$, which are bound to the types \texttt{STUDENT} and \texttt{THESIS}, respectively. The predicate of the record is the relation \texttt{WRITES}, which we can understand as an invariant that is true for all records of this type. 

The question that arises from this is how we can define the structural properties derived from Montague propositions while also retrieving the information about the values of our structure. Here, we can turn to \textit{Type Theory with Records} (TTR). TTR is inspired by Martin Löf's type theory and, in a sense, expands upon the idea of Montague's grammar by introducing a structured object notation \cite{Cooper2005Records, cooper2021structure}. Informally, TTR is a reflective representation of the Montague grammar. The notation for TTR is typically divided into type level and value level.

A record type \( T \) is defined by a set of labels \( l_i \) and a corresponding set of types \( T_i \in T \). The associated record object consists of a set of values \( d_i \), which are assigned to the labels and correspond to the types specified for each label in the record type.

We can then proceed to define the concepts of injectivity and surjectivity in the context of dependent types. From this, we can form a connection between our formalism of record types and the idea of nominal and structural subtyping.

\begin{definition}[Surjective Function]
 A function $f : A \rightarrow B$ is said to be surjective if, for all terms $b : B$, the fiber of $f$ over $b$ is inhabited. Here, we mean to express that for every element in the codomain, there exists an element in the domain that is mapped to it. On a high level, we can think of this as expressing the quantifier of existence or, in the set-theoretic sense, `\textit{at least} one'.
  
  \input{equations/surjective_function.tex}
  
 The notation $\parallel \text{fiber}(f, b) \parallel$ is the propositional truncation of the type expressing the fiber of $f$ over $b$. For our purposes, it's sufficient to understand this as expressing the predicate that the fiber of $f$ over $b$ is inhabited, which is to say that there exists some element or term in the domain that is mapped to $b$. In essence, it simply states the aforementioned quality of existence.
\end{definition}

Surjection has a general correspondence to the more concrete idea of nominal inheritance-based subtyping. Specifically, we can express the idea that if there exists an abstract class $A$, then we will always have at least one concrete class $ B$ that is a subtype of $A$. A key observation to note is that surjection enables us to map multiple elements, in this case, subclasses, to a single element, the superclass. A byproduct of this quality is that we lack the property of uniqueness. We can view this as analogous to the fact that in nominally typed languages, unless we perform a, usually runtime, downcast, an object only has those properties that are defined in its superclass.

\begin{definition}[Injective Function]
 A function $f : A \rightarrow B$ is said to be injective if, for all terms $b : B$, the fiber of $f$ over $b$ is a sub singleton. By which we mean to express that the collection of elements $A$ which are mapped to $b$ consists of either a single element or no elements at all. Here again, on a high level, we can think of this as expressing the quantifier of uniqueness or, in the set-theoretic sense, `\textit{at most} one'.
  \input{equations/injective_function.tex}
\end{definition}

Injection then has a correspondence to the idea of structural subtyping. Structural subtyping, often seen more in dynamically typed languages, relies on implicit structural comparisons to express the idea of substitutability. The key distinction of nominal subtyping is that we preserve the unique quality of objects; in practice, this idea is often leveraged to allow for more flexible uses of existing implementations. The uniqueness of object mappings means that unlike in the case of nominal subtyping, where we typically have to downcast to access the complete set of properties of an object, in the case of structural subtyping, excess properties are preserved and at least in theory, can be accessed without any downcasting as there is a unique mapping back to the original object which preserves the structure.

\subsubsection{Abstract Types \& Substitutability}

In our case, there are two key interrelated things we wish to extend the library with. Firstly, support for abstract types, and from this, support for concrete types that implement this abstract representation. Abstract Data Type's (ADTs) in the theoretical sense means to express a type which encodes a contract or model for a set of behaviors and properties which a concrete variant of this type must adhere to. A basic example could be the abstract definition of a list, which is commonly parameterized with a type argument representing various concrete variants, such as a list of ints or a list of strings. The common semantic properties then include the ability to add, remove, or access elements. A somewhat trivial benefit of this is that unless we must know the concrete type of a list, we can work with this abstract definition and, hence, write more generic code that can work for a variety of concrete variants. Polymorphism is a natural byproduct that comes from the idea of substitutability of ADTs. If an ADT represents an abstract contract with a set of concrete types model, then we can say that any type following this contract could reasonably be substituted in place of this ADT without any behavior change; this is the general idea of polymorphism or, more specifically, behavioral subtyping. Liskov formalized a strict condition of this idea in her Substitution Principle. 

\begin{definition}[Liskov Substitution Principle]
 We denote $\phi (\tau_T)$ as a property provable about objects $\tau_T$ of type $T$. Then $\phi (\tau_S)$ should be true for objects $\tau_S$ of type $S$ where $S$ is a subtype of $T$ denoted $S <: T$. \cite{10.1145/197320.197383}
  \input{equations/liskov_sub_p.tex}
Due to its strictness, the condition is often relaxed in subtyping implementations. Nonetheless, it serves as a good basic formalism for considering substitutability.
\end{definition}  

One common practical instance in which we see behavioral subtyping occur is in the case of interfaces. Interfaces within the context of programming languages refer to implementations of the aforementioned idea of an abstract type. Behavioral subtyping is typically observed in the dynamics of interface implementation. In the case of many nominally typed object-oriented programming languages, this takes the form of an abstract class representing the interface and an inherited concrete class that forms the implementation. It should be noted that while inheritance can allow for subtyping, it does not necessarily imply it. Likewise, the presence of subtyping does not imply inheritance. Another paradigm that has emerged as a solution to the deficits associated with inheritance-based subtyping is the idea of composition-based subtyping, with the familiar phrase being `favor composition over inheritance'. Composition-based subtyping is similarly based on the idea of an abstract interface, which dictates a set of behaviors and properties that a concrete implementation must follow. The key distinction is that a concrete implementation does not inherit from the abstract interface but rather is composed of it. In other words, for composition-based subtyping, the concrete implementation exists as an instantiated version of the abstract interface directly rather than an inheriting subclass. Implementations of composition-based behavioral subtyping are often expressed in the form of protocols, traits, or interfaces, which serve as a contract that a concrete implementation must adhere to. To clarify again, the difference here is that with composition-based subtyping, there is no hierarchical relationship between the abstract interface and the concrete implementation; the concrete implementation is simply a realization of the abstract interface. Composition-based subtyping can be understood more broadly as an implementation of parametric structural subtyping or, more simply, generics, in which substitutability is determined by the structure of the object, which exists as a specialization of the general interface. 

A crucial point of consideration is that since subtyping is a function of a language type system, how do its enforcement properties influence the dynamics of subtyping? We can categorize enforcement into two main aspects: when enforcement occurs and how it occurs. Since we are explicitly concerned with substitutability, the question becomes: when do languages enforce this, and how do they do so? When it comes to the `when,' the trivial approach would be to delineate compile-time and runtime, though as JIT compilers, in a sense, combine the two, it makes more sense to state it in terms of information availability. We can define a hypothetical object $o$ of type $S$. We have a method taking an argument of type $T$ where $S <: T$, the most trivial variant of substitutability would occur in the case where $S = T$, and this is precisely what we tend to see with parametric structural subtyping, here methods are specialized such that for all concrete variants of a type $T$ we have a corresponding concrete method accepting this variant. For statically typed languages, we see this as generic methods being instantiated through means such as the aforementioned monomorphism, although it can also occur using runtime-based approaches. In the case of dynamically typed languages, there is a little more nuance depending on implementation; the untyped case, which is purely structural subtyping, is defined by the semantic properties of how the argument is applied. The typed case refers to dynamic languages that have a gradual type system. Here, there is considerable variation in not only the execution method (interpreted, JIT compiled) but also in the extent of enforcement and application. At one end of gradual typing systems, we have TypeScript, which exists in large part separate from the underlying execution of JavaScript and simply acts as a layer on top of JS.

On the other hand, we have languages like Julia, which, despite having a form of gradual typing, make considerable use of type annotations as a means of more effectively specializing code to minimize runtime compilations. Nominal subtyping, on the other hand, tends to be a predominantly runtime process, regardless of the language, the main reason being that with nominal subtyping, we express substitutability as a function of an explicit hierarchy, as opposed to direct static equality. The hierarchy is then something that must persist and be used for us to determine a valid substitution as opposed to it being trivially and apparent. A notable distinction is that statically typed languages enforce, at compile-time, that abstract methods be implemented in an inheriting class, such that LSP does not end up being violated. In contrast, dynamically typed languages might have their type systems enforce a nominal hierarchy via annotations, but this does not necessarily imply that LSP is met for all properties. The basic takeaway from this is that we can interpret type systems as existing on two spectrums: the extent to which they are integrated and applied within the language runtime and the strictness of the invariants they enforce. 

\subsubsection{Substitutability in Julia and C++}

What we see in Julia is that it enforces nominal subtyping of abstract types in only the most direct sense, which is to say, for a type $S$ and an abstract type $T$, as long as there exists a declared subtyping relationship $S <: T$ then we can use $S$ in place of $T$. The declaration has no enforcement on the actual underlying structure of the object; here, Julia falls back to simple error checks if property access does not resolve. Within Julia, subtyping enforcement is entirely a function of the type declaration, as opposed to any structural qualities of the object. We can see this in more rigorous terms through the work of Zappa et al. \cite{Zappa2018Julia}, which aimed to formalize Julia's implementation of subtyping.

The case of C++ is more complex, as it's a statically typed language. Aside from enforcing a nominal hierarchy like Julia, it also enforces a structural hierarchy to avoid violating LSP ahead of time. Informally, we can say that given a type $S$ and an abstract class of type $T$, for $S$ to inherit from type $T$, it must implement all the abstract methods of $T$, in a sense enforcing that it's a valid substitution. A key difference between this and structural subtyping, or some variants of parameterized structural subtyping, is that in the abstract context, we lose any excess properties of the object. Stated differently, inheritance-based subtyping overlaps with parameterized structural subtyping if it enforces a concrete implementation of abstract methods, with the difference being that we lose trivial access to excess properties (\ie we need downcasting).
